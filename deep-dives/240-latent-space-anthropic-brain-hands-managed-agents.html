把腦留在岸上，把手丟進水裡——Anthropic 怎樣用 Claude 造 Claude

📅 2026-10-27 18:53 UTC·🎙️ 主持：swyx（Shawn Wang）、Alessio Fanelli·👤 嘉賓：Katelyn Lesse、Angela Jiang·⏱️ 約 28 分鐘閱讀

這集表面上是 Opus 5.5 的發布覆盤，實際上是一份「前沿 lab 怎樣把自己變成平台」的工程口述史。三條線交織：模型發布已經變成 API 發布，大部分工作量不在模型本身；Claude Managed Agents 把 agent 的「腦」與「手」拆開，意外換來一個極強的安全屬性；為了撐住用量，Anthropic 用 Claude 把整個 Messages API 從 Python 單體重寫成 Rust——會議室裡沒有一個 Rust 工程師，原本估計要幾年的遷移，幾週內切完流量。

「The two things that mattered most were the plan to do the thing and then the verification of the thing. Because the actual implementation was Claude writing code.」 Katelyn Lesse，談 Messages API 重寫（逐字稿 57:00 前後）。這句話可以當成整集的方法論總結：當實作成本趨近零，規劃與驗證就吃掉全部價值。

一、先講錢：S-1 的兩個迴圈，是這集所有工程決定的背景

swyx 開場一個人講了幾分鐘財務，這不是閒聊。Anthropic 已遞交 S-1，預計兩週內以約 2 兆美元估值上市；成立以來累計募資逾 1,000 億美元，累計燒錢不到 100 億美元。他把公司的敘事拆成兩個迴圈：improvement loop（模型變強 → 產品變好 → 更多人用 → 更多回饋 → 模型更強）與 investment loop（收入 → 算力 → 更大模型 → 更多收入）。

真正支撐這兩個迴圈的是幾個很硬的數字：TTM 人均營收 660 萬美元，一年前是 140 萬；2025 年 Q2 每 1 美元收入虧 0.5 美元，現在每 1 美元成本產生 2 美元收入；一年前每 1 美元收入虧約 126–129%，本季首次 GAAP 盈利 19%。年付費逾 10 萬美元的客戶中，超過一半使用 Claude Platform。

把這些數字放在前面，後面嘉賓講的每一個工程決策就同時是財務決策。CPU 省 40–50% 不是「技術上很酷」，是毛利；延遲改善 10–20% 不是 benchmark 加分，是留存；把對話狀態搬到伺服器端不是架構潔癖，是 token 成本。我的判斷是：這集最值得學的不是任何單一技術，而是把工程語言與財務語言對齊的能力——Katelyn 講 CPU 的時候，她腦裡想的是 unit economics。

二、模型發布＝API 發布，而 API 發布的大部分工作是「不性感」的相容性

Katelyn 把一次模型發布拆成流水線：安全測試 → 內部 antfooding → 切多個版本 → 給第一方產品（Claude Code、Cowork）→ 給 API 早期客戶（Cognition、Cursor 等）→ 修回饋 → 上線。真正耗時的不是模型，而是讓既有的 harness 不被打斷。

她舉了一個非常具體的例子：為了防止蒸餾而要求「跨輪保留 thinking blocks」，會直接弄壞客戶自己手寫的 context compaction 策略。於是 Anthropic 反過來在 API 裡補了一個官方 compaction 功能，讓客戶不必破壞保留規則。這種「我改規則，所以我也要提供替代路徑」的動作，是平台公司與模型公司的分水嶺。

她的原則值得抄下來：區分「要改整合、但事情還做得到」與「事情從此做不到」。只接受前者；後者要全力避免。這條線聽起來簡單，但它是所有平台遷移爭議的根源——大部分「開發者反彈」不是怕改 code，而是怕某種用法從此被宣告為不可能。

三、蒸餾：安全問題，不是商業問題（但我對這個框架有保留）

這是全場最反直覺的一段。外界（尤其中文社群）常把蒸餾理解為「偷模型、搶收入」。Angela 直接把這個框架拆掉：

「Realistically, if you distill from us, you actually pay us. So commercially, we make the money. So it's not really that kind of an impact.」 Angela Jiang，回應「蒸餾是不是商業威脅」。她的意思是：蒸餾者仍然要買 token，錢最後還是付給 Anthropic。

她說真正不能接受的是：被蒸餾出來的模型會脫離 Anthropic 的 safety classifiers 運行，等於把沒有護欄的智慧散佈出去。因此他們願意付出 UX 代價去堵 chain-of-thought 抽取，包括 prefix-lock thinking、跨輪保留、跨帳號濫用偵測；同時提供官方 compaction API 作為補償路徑。

我的判斷：這個框架在「蒸餾者仍透過 API 付費」的前提下成立，但它默默假設了蒸餾的目的只是「用更便宜的模型做同樣的事」。如果蒸餾是為了把能力搬進自己的推理棧、最終脫離 API，那商業邏輯就會隨時間變弱——不是今天，而是三年後。Anthropic 把問題純粹安全化，真誠成分很高（他們確實在乎護欄），但也剛好是最不需要談定價權的敘事。兩件事可以同時為真。

值得注意的是，這個立場會直接影響產品：輸出端防護（thinking blocks、跨帳號偵測）只會越來越硬，靠 API 蒸餾縮差距的路會變窄。對做模型的團隊來說，這是一個需要提前計入的路線風險，而不是道德問題。

四、腦與手：一個為延遲而生的架構，事後被證明是安全架構

Claude Managed Agents（CMA）的設計很簡單，但拆得很乾淨：

  • 腦＝harness＋session log，跑在耐久伺服器上，由 Anthropic 托管。
  • 手＝容器／sandbox，按需建立、可隨時死亡。

第一版其實是「把 Claude Code 塞進 sandbox、外面包一層 API」。問題有兩個：回第一個 token 之前要先開機、開 agent；sandbox 一死，整個 agent 跟著死。重構之後，sandbox 可以死、session 不會死，首 token 也不必等開機。

「There's actually the product manager who worked on this from the very beginning was like, the most important property of this architecture is security. And everyone's like, yes, yes, yes. But latency and reliability… Now they're vindicated. I literally apologized to this person yesterday.」 Katelyn Lesse（1:04–1:05）。她說當初團隊禮貌地點頭，心裡想的是延遲與可靠性；直到最近 sandbox 逃逸事件頻傳，安全才變成主角。

這個故事很容易被讀成「堅持的人最終是對的」，但更準確的讀法是：好的架構決策經常是多重理由的疊加，而當下只有一個理由說得出口。腦手分離同時改善了延遲、可靠性、成本與安全；團隊當時用延遲與可靠性說服人，因為那是最容易量化的。安全是後來的紅利，不是最初的設計目標。

五、憑證不在 sandbox 裡：這才是「腦手分離」最值錢的部分

如果 agent 要呼叫 MCP server、CLI 或第三方 API，就需要憑證。舊世界的做法是把憑證送進 sandbox，然後想辦法「scrub」——祈禱 agent 不會把它讀出來、寫進檔案、或帶到別的請求裡。Anthropic 的做法是物理隔離：

「We have a totally separate vault where those credentials are getting stored… the agent only ever sees like a placeholder. And on egress, we have a proxy that goes and pulls the right credential out and injects it… the agent is never in the same place where the credentials are.」 Katelyn Lesse（1:05–1:06）。搭配 domain allowlist，sandbox 甚至可以完全斷網。

這個設計的威力在於它改變了失敗的代價。如果 sandbox 被逃逸，攻擊者拿到的是一個沒有憑證、沒有網路、只有 placeholder 的盒子；真正的 secret 在另一個系統裡，只在 egress 的那一刻被注入到一個受控的連線上。sandbox 隔離不再是唯一防線，而是縱深防禦的一層。

我的判斷：這是 2026 年 agent infra 最應該被抄的一條。不要把「執行不受信任的程式」與「持有憑證」放在同一個信任邊界內。多數自建 agent 系統仍然把 API key 放在環境變數裡、把 sandbox 當成唯一的牆；一旦模型開始寫自己的工具、自己找路徑，這堵牆就會顯得非常薄。

六、trust grants：為「希望永遠不會發生的事」建基礎設施

Fable 被政府要求下架（de-deployment）之後，團隊立項做「一鍵全量回收」。更關鍵的是那個為了 cyber／bio 驗證計畫而建的授權層——他們叫 trust grants，本質上是 Anthropic 自己的 IAM：把「誰可以用哪個模型、哪個放寬護欄的計畫」一路授權到請求熱路徑上。

Angela 說這是產品管理的範式轉變：傳統 PM 依序列下注，但在前沿 AI，極端事件機率非零且無法預測，只能像避險基金一樣建一個「對沖組合」，寧可為低機率事件先做通用 primitives。結果那個原本只為驗證計畫而建的授權系統，後來長成通用能力：模型存取、trusted access 計畫、模型下架，全都復用它。「從正常產品角度這很不合理，但我們越來越常伸手去拿它。」

這段話的份量被低估了。它描述的不是一家 AI 公司，而是一個正在長出準國家能力的組織：身分、授權、分級存取、撤回機制、合規審計。當模型能力被視為戰略物資，平台就必須具備物資管制的能力；而物資管制一旦建成，它自然會成為整個產品線的底層。這是「安全」與「平台」合流的地方。

七、CPU 是新的算力瓶頸，而且是內部的零和遊戲

所有人都在談 GPU。Katelyn 說 CPU 一樣緊：product services、API、sandbox（產品與研究各一份）、還有因為程式碼變多而暴增的 CI。她那句「你不能再按需擴容，現在要提前做 capacity planning」，在訪談裡出現的語氣近乎抱怨——因為它意味著工程團隊要開始對研究團隊說不。

更麻煩的是，Anthropic 同時跑在三家雲上，因此不能假設任何特定機器形狀，只能靠最 vanilla 的資源與自家效率優化。這反過來解釋了為什麼 Rust 重寫是策略級別的決定：當你無法靠買更多機器解決問題，唯一的路是讓每個請求更便宜。

數字CPU 節省 40–50%（Katelyn 先說「order of magnitude」，隨即修正為 ballpark 40–50%）；time-to-first-token 改善 10–20%，長任務更明顯；團隊原本 Rust 經驗 0 人；Messages API 由單一 GCP region 的 Python 單體，變成多雲多區域。
八、Rust 重寫：零 Rust 團隊、整條 fork、shadow traffic 對帳

這是全場技術含量最高的一段，也是最容易被標題化的一段。拆開來看，方法論其實很清楚：

  1. 不做漸進式遷移。他們沒有把 API 一小塊一小塊換掉，而是直接 fork 出整條 API 的 Rust 版本。
  2. shadow traffic。把真實流量同時打進 Python 與 Rust，逐一比對輸出是否一致。
  3. feature flag 切流。確認一致之後，用負載平衡與開關逐步把流量移過去。
  4. 拒絕 scope creep。這是一次純 port——他們刻意不加新功能，因為本體團隊還在同一時間往舊系統加功能，還有靜態分析在旁邊盯著兩邊同步。
「We don't have a single Rust developer in the room… Claude is going to write the code. The humans design the system.」 Katelyn Lesse（56:30–57:30 一帶）。她補充：真正重要的是「計劃」與「驗證」，實作本身已經不是瓶頸。

值得注意的是，這不是「AI 寫 code 好快」的故事，而是驗證成本可以被工程化的故事。兩個系統輸出要一致，這件事有客觀標準；可以自動化、可以大規模跑、可以在不確定的地方停下來。正因為驗證被做得足夠嚴，才敢讓一個沒有 Rust 經驗的團隊在幾週內切核心 API。

我的判斷：這個案例的通用版本是——當你能把「正確」定義成可機器比對的差分，遷移就從「幾年的人力工程」變成「幾週的驗證工程」。反過來說，凡是「正確」只能靠人逐行閱讀來判斷的工作，AI 帶來的好處會小得多。這也解釋了為什麼 Anthropic 內部對「軟體工程被解決」這句話如此謹慎：他們解決的是有驗證器的那部分。

九、Eval 是新的工程紀律，而大多數 agent 產品根本沒有 eval

Katelyn 說早期客戶的回饋「非常 unstructured」，就是一個 Slack channel：「這東西怪怪的」。能進 early access 的客戶，是那些有完整 eval suite、能快速給可執行回饋的人。她的建議是「只會太少、不會太多」：靜態測試、LLM-as-judge、pairwise 比較都要，然後讓 agent 幫你演化 eval。

Angela 補了方法論：把工程當研究做——先定義目標、形式化成 eval、再看失敗是 eval 錯、環境錯、還是模型錯。她特別強調：「很多時候是你的 eval 錯。」

這段與 10-27 MLST 的 Lean 那集形成一個很漂亮的對照：一邊講形式化如何暴露人類數學的隱性假設，一邊講 agent 系統要靠驗證（shadow traffic、eval、測試）而不是逐行審查來守品質。同一個時代方法論，一個用在數學，一個用在基礎設施。

十、兩個未解難題：個人化，與路由的 UX

swyx 問：「每個人的 CLAUDE.md 都不同，你要怎麼調？」Angela 答得極坦白：

「We don't do a great job of it. Seriously, it's really hard.」 Angela Jiang，談模型個人化。她說目前只能靠更多參數（effort level、模型大小、按 free／prosumer／Claude Code／Cowork／Enterprise／API 分群的預設值），加上在互相衝突的回饋之間做品味判斷。

她承認這不可規模化，長期要讓 Claude 真正吸收使用者的個人化訊號。順帶披露：Claude Code 的預設 reasoning effort 已改為 medium。

路由與 fallback 是同一類難題。用一個較笨的分類器去判斷要不要把請求降級，必然誤判；而且使用者不知道自己的任務會被路由到哪裡。Angela 認為暴露路由邏輯不是好 UX，跨模型切換還會造成人格不連續；她更看好「單一模型、可連續縮放的努力程度」，至少人格一致。API 層面他們提供伺服器端 fallback 與 SDK 端 helper，讓客戶自己選。

我的判斷：這是整集最誠實、也最容易被忽略的一段。整個行業都在講「模型會自己選工具、自己選模型」，但真正的產品問題是當系統替使用者做了決定，使用者能不能理解、能不能預期、能不能反悔。Anthropic 的答案是「盡量不要讓使用者看到路由」，這在體驗上合理，在信任上卻是一個賭注。

十一、Dreaming：不是新模型功能，是「managed agents all the way down」

外界容易把 Dreaming 想像成某種神祕的記憶機制。實際上是：

「We spin up another managed agent that can inspect the previous managed agent and then write memories to that managed agent. So it's managed agents all the way down.」 Katelyn Lesse（46:30 一帶）。Dreaming 是「CMA on top of CMA」。

這個設計哲學很重要：底座 harness 刻意保持簡單、不強加意見，把「hill climbing 策略」留給上層組合。Dreaming 只是第一個示範；同樣的 primitives 可以組出 best-of-N、verifier agent、parallel agents。他們說即將釋出让開發者自建 multi-agent 策略的 primitive 與模板。

同時他們也承認：memory 與 skills 的投入「放緩了一點」，因為模型發布帶來的安全工作吃掉了團隊大部分精力。這是整集少見的、對外敘事與內部優先級不一致的時刻——上半年「memory 是重點」的說法，在這裡等於被側面修正。

十二、多 agent 的唯一架構建議：共享狀態＋子 agent 不阻塞
「It needs a shared state and it needs to not block its sub-agents. As long as you contain those two principles, honestly, I think people should experiment and probably try some really crazy stuff.」 Angela Jiang（1:45）。她認為「角色由 agent 自己指派」是這一代的新東西，並預期 Claude 會越來越會「把自己切開、複製自己、調整架構」。

這句話的實作含義比聽起來深。共享狀態意味著子 agent 不應該各自維護一份世界觀；非阻塞意味著一個子 agent 卡住不應該拖死整個 parent。兩者合起來，其實是在要求把 agent 當成分散式系統來設計，而不是當成一個更聰明的函數呼叫。

十三、反 slop：人類對品質負責，讀者有權把垃圾退回去

Anthropic 內部的規範是：可以用 Claude 幫忙，但你不能沒讀過就丟給同事，那是把解析成本轉嫁給消費者；如果真的是 slop，「就退回去」。同時她也提醒不要過度神經質——看到一個 em dash 就認定是 AI 寫的，也是一種無效反應。

「If it really actually is just slop, like send it back. Like, just say no.」 Katelyn Lesse（1:23 一帶）。她說這條線很難畫，團隊內部也天天在吵。

工程端的對應做法是：人類負責系統設計，Claude 負責實作，靠完整的驗證（測試）而不是逐行 review 來守品質。這與 Rust 重寫那段的邏輯完全一致——把品質問題轉換成驗證問題，而不是轉換成更多的人工閱讀。

十四、pacing 與「11 天後再發一個模型」不矛盾

swyx 直接問這個表面矛盾。答案很簡單：pacing 不是減速的口號，而是「三個維度的安全檢查都過了才發」。Katelyn 把它拆成：

  1. 架構與基礎設施安全（sandbox、憑證、網路）。
  2. 線上護欄（模型運行時的 classifiers、fallback）。
  3. 離線護欄（對靜態資料做分類、審查）。

再加上每個模型不同的政策：Fable 有資料保留要求，Opus 5.5 沒有；cyber 驗證計畫、生命科學驗證計畫；以及 trust grants 授權層。Opus 5.5 在三方面都達標，所以發。

我的判斷：這個回答在邏輯上成立，但它把「pacing」定義成「自己的門檻」，而不是「行業的節奏」。對一家已經被視為前沿的 lab 來說，這兩者會互相影響；當你發布，別人的時間表就被壓縮。這是這集沒有處理的問題，也是外界質疑的真正所在。

十五、工作負載正在遷移：簡單任務飽和，長時程 agentic 仍未飽和

Angela 觀察到，部分任務的 intelligence 已經「飽和」——再加智慧也換不到多少價值；真正還有 alpha 的是過去無法暴力破解、需要極長時程的 agentic 工作，以及 bio、cyber 這類硬科學／硬工程問題。她認為這類工作比外界想像的多，也是新創可以「彈射」上去的地方。

這個觀察與整集的架構敘事互相呼應：如果價值集中在長時程任務，那麼「腦不死、手可換」就是必要條件；如果價值集中在短任務，sandbox 開機時間根本不重要。Anthropic 押的是前者。

十六、我的判斷：三個可以直接搬走的框架

一、把「驗證」當成一等公民來投資。這集裡所有驚人的效率數字，背後都有一個可機器比對的正確性定義：shadow traffic 的輸出 diff、eval suite、測試。沒有驗證器的地方，AI 只會讓你更快地產出無法確認的東西。

二、檢查你的信任邊界，而不是你的防火牆。憑證 vault＋egress proxy 的設計，本質上是承認「sandbox 一定會被逃逸」，然後讓逃逸後的收穫接近零。這是比「把 sandbox 做得更牢」更穩健的思路。

三、為低機率事件建通用 primitives。trust grants 的故事值得每一間做平台的公司抄：不要為「某個具體災難」寫死流程，要為「任何需要撤回、分級、授權的災難」建一套通用機制。它的回報不會出現在 roadmap 上，但會在你最需要的那天出現。

要保留的三個懷疑：

  • 「蒸餾者仍然付錢給我們」在短期成立，長期取決於蒸餾後是否能脫離 API；把問題完全安全化，會掩蓋定價權的變化。
  • 「零 Rust 工程師、幾週重寫核心 API」是驚人成就，但外界無法驗證 shadow traffic 的覆蓋率與 diff 的嚴格程度。流程正確不等於結果可審計。
  • 「pacing 是我們自己的門檻」這個定義，避開了「前沿 lab 的發布會改變別人的時間表」這個更難的問題。
核心這集真正的主題不是 Opus 5.5，而是「當實作變便宜，瓶頸會轉移到哪裡」。Anthropic 的答案有三層：規劃（人類設計系統）、驗證（shadow traffic、eval）、隔離（腦手分離、憑證 proxy）。三層都做對，才有資格說「我們用 Claude 造 Claude」——否則那句話只是把風險說得很好聽。
