「Computer Use 已經 180 度不同」——Latent Space × OpenAI DevDay 2026：Dwarkesh 錯在哪，同 OpenAI 點樣一星期克隆咗 Jev

📅 2026-09-30 22:23 UTC（北京 10-01 06:23）·🎙 Latent Space（主持 swyx ＋ Vibhu）·👤 嘉賓：Ari Weinstein（OpenAI Computer Use 產品／工程負責人）＋ Nikunj Handa（OpenAI API 產品負責人）·⏱ 約 40 分鐘·🏷 Computer Use / API / Agent 基建

呢集係 DevDay 當日、直播一完就錄嘅「第一手復盤」。上半場由 Ari Weinstein 講 Computer Use 呢幾個月點樣「180 度不同」——正面反駁 Dwarkesh 早前「Computer Use 兩年冇進展」嘅講法；下半場由 Nikunj Handa 拆 OpenAI 新一輪 API 原語，重點係一個被 Jev 啟發、四星期前根本唔喺 roadmap 上、一星期內做出原型嘅 Decisions API。以下內容按官方頁面完整逐字稿（約 57 KB）整理，引號內全部係逐字稿原文。

一句話總結

呢集有兩條主線，其實係同一件事嘅兩面。第一，Computer Use 嘅瓶頸已經由「模型識唔識做」轉移到「做嘢本身幾慢」——代理已經識 debug、識自我恢復、識寫 JavaScript 一次過做多步，於是開始撞到「等 doordash 載入」呢類世界本身嘅物理限制。第二，當一個領先嘅推理 API（Jev）出現，OpenAI 內部嘅 hacker 文化令佢一星期就克隆出等價原語——而且坦白承認「完全冇訓練新模型，就係 Luna 零樣本」。兩條線合起來講同一個判斷：呢個行業嘅護城河，正被壓縮到以「星期」為單位；而真正稀缺嘅，係推理棧效率、快取基建、分發同可靠性。

「你其實係喺造一朵 AI 雲……你做緊 AI 原生嘅 EC2、S3。」 —— swyx 總結 OpenAI 平台戰略（逐字稿原文）

一、背景：Dwarkesh 嗰條「唔識答」嘅問題

節目開場直接擺出衝突。三個月前，Dwarkesh 喺佢嘅 RLVR 影片essay 入面問咗一條「令我困惑又覺得有意思」嘅問題，仲搞到一班 Computer Use 圈嘅人好唔高興：

「Why has progress on computer use been so slow? Computer use is so clearly verifiable.（點解 Computer Use 嘅進展咁慢？Computer Use 明明係咁明顯可以驗證。）」 —— Dwarkesh Patel，2026-06-27，604K 瀏覽

Dwarkesh 嘅答案係：「一個領域淨係『可驗證』係唔夠嘅。」而 Latent Space 呢集，就係請咗最有資格反駁嘅人嚟反駁。swyx 自己亦都講到明立場——佢哋去過 Anthropic 嘅 Computer Use 發佈會、做過 Claude Cowork 第一個大 podcast、搞過 AIE 第一屆 Computer Use track、而且接近過 OpenAI 收購 Sky Software 呢單案，「所以今日第一位嘉賓 Ari Weinstein 係好合理嘅」。

二、「180 度不同」：三個具體變化

Ari Weinstein 嘅職涯主線就係「電腦自動化」：Apple（Shortcuts）→ 創辦 Sky（後被 OpenAI 收購，即今日 Codex Computer Use 嘅技術來源）→ OpenAI。佢對 Dwarkesh 嘅回應好直接：

「佢哋幾個月前講嗰句……我希望佢而家有唔同嘅睇法，因為 Computer Use 已經係 180 度不同於佢以前嘅樣。」 —— Ari Weinstein

咁「180 度」具體變咗喺邊？Ari 給出三個可操作嘅變化：

  • 由「開到頭就卡死」變成「擅長 debug、擅長重試」。Ari 原話：「以前它們能夠可靠地開始任務，但一遇到問題就卡住；現在它們非常擅長 debug、擅長重試、擅長自省邊度得邊度唔得。」——呢個係佢心目中最大嘅 delta。
  • 唔再「一步一截圖」，而係寫 JavaScript 一次做多步。「你手動展開 tool calls 就見到，佢唔係一次做一個動作，而係真係喺寫一段 JavaScript，由電腦執行，有時一次過做好多個動作。」
  • 多模態介面並用。「模型可能用截圖、可能用 accessibility、可能用 Playwright……按任務切換。」Ari 特別點名過去 Computer Use 產品「花好多時間喺度 scroll」嘅痛點——截圖、scroll、再截圖——而 accessibility 同直接 DOM 存取，令模型「一次見到成版或者成個 app」。
類比Ari 提到一個好傳神嘅細節：accessibility 技術本來係為咗幫有無障礙需求、用 screen reader 嘅人，「結果同樣嘅技術對 LLM 用電腦都好有幫助」——即係幫人嘅基建，意外變成幫 AI 嘅基建。

三、由「比人快」到「字面超人」

全集最響嘅一句判斷，係 Ari 講 Computer Use 已經快過普通人：

「我認為真正瘋狂嘅係，團隊喺過去幾個月做到嘅，係 Computer Use 而家完成任務比普通人仲快……而下一個前沿，係令佢字面意義上嘅超人——真正同專家一樣快、甚至更快咁用軟件。」 —— Ari Weinstein

佢解釋咗點解「超人」係關鍵門檻：一旦達到，就能支撐更即時嘅產品體驗，亦會令用戶「開始默認將某啲以前習慣親手做嘅嘢交畀 agent」。以下是逐字稿中幾個具體數字：

備餐訂單 2 小時 → 15 分鐘（快 8 倍，慳 2 小時）Ari 個人用例：高度客製化嘅 meal prep 落單，用 GPT-6.1 Sol 完成

四、瓶頸轉移：由模型轉向「世界本身」

呢節係全集技術含量最高、亦最容易被忽略嘅一部分。Ari 講到，當 Computer Use 越嚟越快，佢哋越嚟越被「做一個操作本身嘅耗時」卡住：

「我哋發現 Computer Use 越快，就越嚟越被『做一個操作嘅速度』瓶頸住。例如你自動化 doordash.com 上嘅一個任務，好多時間其實係喺度等 doordash.com 自己載入。」 —— Ari Weinstein

佢同 swyx 嘅往來揭示咗一層好深嘅工程現實：理想係 event-driven（例如 JavaScript 嘅 load event），但「有啲事件本質上真係冇得事件驅動」。Vibhu 舉咗個好例子——同客服 chat，對方回覆可能 30 秒、可能 3 分鐘。於是「幾時觸發 LLM 做下一個動作，本身就係一門統計科學」。

我嘅判讀：呢段係對「Agent 會唔會一直加速落去」嘅一個誠實修正。當模型同 harness 嘅延遲壓到好低之後，剩下嘅延遲唔再係 AI 問題，而係人類互聯網嘅負載時間。呢個意味住——下一輪 Computer Use 嘅競爭，會由「模型幾聰明」轉向「邊個更識同一個慢嘅世界打交道」：event 偵測、polling 策略、容錯重試。呢個係枯燥但護城河型嘅工程。

五、App Shots：呢個「截圖」唔係截圖

Ari 特別澄清一個大眾誤解（Vibhu 都話「好多人連 App Shots 係咩都唔知」）：你 double-hit command，睇落好似拉咗一張截圖入嚟——「但佢其實係將所有 metadata、所有 code、所有嘢拉晒出嚟」。

「如果你影一張有連結嘅網頁截圖——截圖唔包含個連結去邊；你影你嘅日曆，event 標題係被截斷嘅。但當你 take 一個 app shot，佢就畀語言模型關於所有嘢嘅完整脈絡。」 —— Ari Weinstein

Ari 仲教咗一個「nerd 玩法」：喺 Codex 入面 take app shot，點開附件右上角粒細掣，你就見到原始文字同原始 accessibility 表示——「我哋花咗好多工夫 dump 晒出嚟，同時令佢 token-efficient，呢度有啲藝術成分」。

六、最深遠嘅用例：代理測自己嘅代碼

Ari 主動提出佢心目中最重要嘅 Computer Use 用例，而且講明「比聽落去重要得多」：

「以前你喺 Codex 建咗個嘢，Codex 幫你建好，然後你要自己測——你就變咗個 agent 嘅 QA。而家用 Computer Use，你可以完成成個 SDLC：agent 建軟件，agent 測軟件。到我手上嘅時候，佢已經 work 咗。」 —— Ari Weinstein

佢跟住補咗一句好可愛嘅自我指涉：「我有額外嘅樂趣，因為有時我係喺度開發 Computer Use 本身，於是我有一個 Computer Use agent，用緊我嘅 Computer Use agent，再用緊另一啲嘢。」swyx 亦分享咗自己嘅「visual play test skill」——專門捉一啲「淨係睇 code 睇唔到」嘅設計問題，仲可以用嚟逐屏 clone 一個 SaaS（「如果你用緊一個差嘅 SaaS，想殺咗佢，就 clone 佢」）。

七、Agents API 與信任基建：權限先於效率

Computer Use 今次入咗 Agents API，開發者可以用「同一套 OpenAI 自家 Codex、ChatGPT 用緊嘅 Computer Use」。Ari 講咗一個好關鍵嘅建議，同之前 Thariq 嗰集（179）互相呼應：

「你可以自己建 Computer Use harness，但好難。而且我哋係喺自己嘅 Computer Use harness 上面訓練模型，所以用同模型 distribution 一致嘅嗰個，會有速度、成本同準確度嘅優勢。」 —— Ari Weinstein

講到安全，Ari 嘅口徑係工程同信任基建，唔係治理：

  • 逐步建立信任：「我哋都仲喺過程之中，而且我哋之中有啲人比世界上多數人更早學會信任呢項技術……所以有責任透過做可靠嘅嘢、做啱嘅安全檢查、喺做後果性操作（例如付款）之前取得用戶同意，去逐步建立信任。」
  • 最小授權：「視乎應用，確保佢只可以訪問佢真正需要嘅網站或 app。」
  • 但主持人自己就係反例：swyx 自曝「我畀佢配置 DNS、畀佢幫我找咭數，好幾萬美金嘅嘢就咁 yolo 畀 Computer Use，『最壞可以點？』」——呢個係早期採用者風險胃納嘅活生生寫照。

八、Decisions API：一星期克隆 Jev

下半場轉去 Nikunj Handa（OpenAI API 產品負責人，入職約三年，前 Stripe）。swyx 一開波就問到最尖：

「你哋幾快見到 Jev 就覺得『嘩』？」——而 Nikunj 嘅回答係 … 「首先要大大 props 畀 Diogo 同 Jev 團隊，真係啟發咗成個市場 segment……好多 OpenAI 嘅人即刻被 nerf sniped（勾起好奇心），話『我哋點樣令呢樣嘢 work？』——但係唔訓練新模型。」 —— Nikunj Handa（swyx 追問：四星期前呢樣嘢根本唔喺開發雷達上）

時間線更誇張：Decisions API 由 inference 同 infra 團隊「自發動手」，做出原型、即刻開始爬延遲，目標係「一旦達到延遲目標就推出」。Nikunj 講嘅係「一星期」級別嘅 sprint。

九、真相：完全喺 Luna 上零樣本

呢節係全集最「爆」嘅披露。swyx 逼問：Decisions API 係唔係只係「結構化輸出 + 關咗 reasoning」——即係人人可做嘅 Jev 克隆？Nikunj 答得好坦白：

「我哋冇為呢樣嘢訓練新模型。我哋純粹建立喺同一批 Luna 權重之上……基本上就係喺 Luna 上零樣本施作，睇吓點。」 —— Nikunj Handa

咁 Decisions API 到底做咗咩？逐字稿提出四層：

  1. 約束（constrained／structured output）——你定義問題同可能答案；
  2. 推理棧優化——針對 TTFD（time-to-first-decision）；
  3. 並行批次——多條問題一次過 batch 跑（所以你唔係等一個答案，而係一次過拿一批）；
  4. 視覺免費附送——swyx：「Jev 冇視覺，你有」，Nikunj：「係，Luna 免費送嘅。」

同時佢亦老實講咗代價：Decisions API 冇 reasoning、係細模型，所以「唔係太擅長長程、複雜嘅任務」，OpenAI 自己都話「點樣將兩條路線結合，仍然係開放研究」。

十、護城河喺邊：校準與置信度

呢段係全集最有 insight 嘅一小節。swyx 指出：如果 Decision 模型同 Luna 同價、關咗 reasoning、加結構化輸出，咁「我就有一個 Jev 啦，係唔係？」——佢自答：「唔係。因為仲有 confidence。」

「RLHF 基本上會令你往你想聽嘅方向坍縮……但唔會保留『你到底有幾大把握』嘅訊號。」——swyx
「我急不及待想睇佢點發展……呢啲可能就係未來模型要 hill climb 嘅關鍵領域。」——Nikunj Handa —— 逐字稿原文

換句話講，OpenAI 承認：首版 Decisions API 未體現真正嘅差異化（校準），要等後續模型。swyx 亦提到業界對 Jev 架構嘅兩大猜測——(1) 擴散式非自迴歸生成、(2) 機械可解釋性直接讀取激活再輸出——Nikunj 都冇證實，只話「呢個空間畀人踢開咗，大家會互相學習」。

我嘅判讀：「Decisions API」呢個名，本質上係 OpenAI 將一個社群自發嘅 pattern 官方化。佢真正嘅戰略意義唔在於技術（零樣本、冇新模型），而在於分發——把一個原本要開發者自己砌嘅低階原語，變成平台上一個有 SLA、有快取、有批次嘅一等公民。呢個正係「AI 雲」邏輯：唔係贏在發明，而係贏在把好 pattern 變成基建。

十一、新 API 原語：由「模型唔停手」到「推理中途插話」

Nikunj 逐項拆解 GPT-6 嘅新 API 能力：

原語作用
Async tool calling工具呼叫耗時長時，模型唔使停低推理——kick off 工具後繼續 reasoning，遲啲再返嚟檢查結果
Mid-turn steering推理途中注入訊息（「工具跑完，你可以放低指令入去」）。swyx 追問呢個係唔係模型對齊能力，Nikunj 確認「係，要訓練入去」
WebSockets雙向通訊底座；最早為 GPT-5.3 Codex Spark 上線
UltraFast 推理「理論上可以攞到嘅最快速度、智能前沿」；Nikunj 話先係壓成本（令 Luna 減價 80%），而家轉去「跑得最快」

值得一提嘅「大象在房間裡」一問：swyx 指出 GPT-5.3 Spark 明確歸功 Cerebras，而「UltraFast 係唔係都同 Cerebras 有關，你哋唔確認亦唔否認，但大家care，而你哋又有自研硅」——Nikunj 冇正面答。

十二、快取與壓縮：枯燥但係護城河

下半場後段係「性能工程」時間，兩個關鍵：

  • 快取（caching）：30 分鐘保證 →（preview 中）12 小時保證；付較高 cache write 費即可鎖定長窗口，令「單線程、無限長」嘅個人 agent 隔三四個鐘返嚟都仲有 cache 效益。另有 cache pre-warming 同 cache diagnostics 工具，官方建議「以 cache-aware 方式設計應用」。
  • 壓縮（compaction）：三條路——Agents API 內建；Responses API 嘅 server-side compaction（過閾值自動壓）；同 /compact（手動、全控制，大型 coding agent 偏好）。Nikunj 透露 Codex 開源 harness 已實作檔案式嘅新壓縮實驗。

十三、「AI 雲」：更高階嘅原語之爭

收尾最有格局。Nikunj（前 Stripe）用 Stripe 類比：「喺 Stripe，遊戲就係喺核心支付原語之上，建更高階嘅 primitives 同產品；我一路好奇 AI 世界對應物係咩。」佢列出一堆開放問題：Agents API 應該畀幾多彈性？memory wall 點設計？storage 抽象要唔要包？「幾多嘢應該 build 入 API，係我成日諗嘅問題。」swyx 一句總結：「你係喺造一朵 AI 雲……Sam 一年前講過，你係喺做 AWS 嘅發明，但做 AI 原生版本，呢個係 EC2、嗰個係 S3。」

十四、爭議點 / 需要打折嘅地方

  • 「比普通人快」缺乏公開 benchmark。Ari 話「無論點量都有好一致嘅 gains」，但強調唔同 harness 配置各異、冇單一公開數字；7 倍係 keynote 口徑。
  • Decisions API 首版係唔係只係命名？swyx 直指「結構化輸出 + 關 reasoning，人人可做 Jev」；OpenAI 承認差異化（校準）尚未在首版體現。
  • 安全靠「自己 dogfood 完再教開發者」。付款等後果性操作要求用戶同意，但主持人自曝「把十幾萬美金 yolo 畀 Computer Use」，暴露早期採用者嘅風險胃納。
  • UltraFast 硬件來源講一半。Cerebras 只喺 5.3 Spark 上被明言，UltraFast 唔確認亦唔否認。

我嘅解讀：護城河嘅時間尺度被壓縮到「星期」

呢集最值得記低嘅，唔係任何單一數字，而係一個速度事實：一個領先推理 API（Jev）出現後，OpenAI 喺一星期內克隆出等價原語，而且「四星期前呢樣嘢完全唔喺 roadmap 上」。呢件事推翻咗一個常見假設——「護城河係『邊個先想到』」。
