把分類器撒進代碼裡
——Jev 的生產客戶，與「決策原語」的第一次實戰

〈The Jev Revolution: What Engineers Are Already Building with System One Models〉
出品：Latent Space·作者：Richard MacManus·場合：AI Engineer Code Summit, San Francisco
發布：2026-11-12 13:08 HKT（05:08 UTC）·約 4 分鐘閱讀（現場報導）
主講：Diogo Almeida（TypeSafe AI 聯合創始人兼 CEO）·講者：Chinmay Goyal（Glean）、Chibi Vikram／Kevin Bernstein（UiPath）、Scott Roberts（Workday）

這不是一集訪談，是一場發佈會級的現場報導。但它的價值不在「誰上了台」，而在一個很少被公開展示的東西：一個新的模型類別，怎樣在兩個月內從 demo 走進 Glean、UiPath、Workday 的生產代碼。

先把場景定住。2026 年 11 月 12 日，AI Engineer Code Summit 把整條「system one」軌道交給了 TypeSafe AI 的 Diogo Almeida。所謂 system one model，指的是非生成式模型：它不逐 token 寫字，而是直接回傳結構化的選擇、分數或機率。相對於推理型 LLM（system two），這類模型快一到兩個數量級、便宜一到兩個數量級——代價是它只會回答「哪一個」，不會回答「為什麼」。

不到兩個月 Jev 於 2026 年 9 月發布，發布當日上了 Latent Space，成為該節目年度最受歡迎的一集；11 月 12 日，它已經在 AIE Code 拿到一整場 keynote。
$100M ARR TypeSafe 在 Jev 發布後約兩個月跨過的年化收入（AINews 同期報導）。
三種生產模式 零樣本分類（Glean）、錦標賽式排序（UiPath）、推測式預填（Workday）——同一顆模型，三種完全不同的用法。

這場演講真正值得記住的，不是「Jev 很強」，而是它給出了一個可以立刻照抄的架構主張。而這個主張，在當天下午就被 Google 用一個 API 定價逼到了牆角。這是本文要處理的張力。

一、核心主張：分類呼叫應該下沉到函數級

Almeida 的整場演講，幾乎不談模型架構，全談「怎麼用」。他的中心句是：

「Code is the language of automation, therefore you need to integrate with code.」 —— Diogo Almeida, TypeSafe AI，AIE Code 2026 keynote

這句話聽起來像廢話，但它其實是對過去兩年 AI engineering 主流做法的一次正面否定。主流做法是：把 LLM 包在應用外面，用 prompt 拼接上下文，然後祈祷它輸出可解析的格式。Almeida 的主張相反——把決策點打散，塞進應用代碼的每一個需要判斷的地方，讓每一個 if/else 的位置，都變成一次幾毫秒的分類呼叫。

swyx 的轉述更直接：應該「大方地把 system one 呼叫撒進應用代碼各處」，用這種方式做出更聰明的軟件，而不是繼續做「把字符串拼起來、然後希望最好」的 AI engineering。

這裡有一個容易被忽略的推論：如果決策是函數級的，那麼軟件的形態會變。 傳統軟件是「邏輯 + 資料」；加上決策原語之後，軟件變成「邏輯 + 資料 + 一層可校準的判斷」。UI 可以邊打字邊預測、後端可以邊收日誌邊分類、檢索可以邊召回邊淘汰。這些都不是「加一個 chatbot」，而是把判斷力變成基礎設施。

二、可靠性：對標邏輯閘，而不是對標 LLM

這場演講最誠實的一段，是 Almeida 承認 LLM 的問題不是「不夠聰明」，而是「不穩定且不可分辨」。

「You get Einstein 95% of the time, but Mr. Bean 5% of the time. And if you can't tell which is which, how the fuck are you going to automate anything.」 —— Diogo Almeida, TypeSafe AI

這句話的重點在後半句。95% 的正確率在 demo 裡很好聽，在生產裡卻是災難——因為你不知道哪 5% 會出錯。一個無法標記自身不確定性的系統，等於把隨機故障藏進了自動化流程。Almeida 的解法是 confidence：每一個答案都帶一個可校準的分數，讓上層代碼可以決定「這一次要不要交给人」。

他把目標講得很高：Jev 應該「和第四個邏輯閘一樣可靠」。意思是開發者應該能像信任 AND／OR 一樣，信任一次分類呼叫——把它當成原語，而不是賭注。這是一個很好的修辭，也是一個很難的承諾：邏輯閘的錯誤率是零，而任何統計模型的錯誤率都不是零。真正可比的，不是「零錯誤」，而是錯誤率已知、且不隨分佈漂移而失控。

讀法：「像邏輯閘一樣可靠」不是說它永遠對，而是說它的失敗模式應該是可預期、可觀測、可降級的。這是把模型當「基礎設施」而不是「智能體」的分界線。
三、Glean：買方要的不是快，是「不用重訓」

如果說 Almeida 給的是願景，Glean 的 Chinmay Goyal 給的就是採購理由。Glean 把 system one 模型與 LLM、其他分類器並用，最適合的場景是零樣本彈性。

「As the taxonomy of the decision space changes, we don't have to fine-tune these models again and again.」 —— Chinmay Goyal, Glean

這句話比任何 benchmark 都重要。企業搜尋與知識管理的痛點，不是「分類不準」，而是分類體系一直在變：新部門、新產品線、新合規類別、新客戶術語。用傳統分類器，每一次 taxonomy 變動都要重標數據、重訓模型；用一個能讀自然語言標籤的決策模型，改的是 prompt 裡的選項，不是權重。

Goyal 在會後訪談中還補了一句，直接點出產品哲學：

「Jev powers a significant number of flows [but] the user just needs to have a product that works; that is always our aim with building anything. So we want to hide away all the complexity of whether we are using Jev or we are using a full-blown LLM.」 —— Chinmay Goyal, Glean，會後訪問 Latent Space

這句話有兩層意思。第一層是產品層：用戶不應該知道背後是哪種模型。第二層是架構層：Jev 與 LLM 不是替代關係，是路由關係。 簡單判斷走 Jev，複雜推理走 LLM；系統的智能不是來自單一模型，而是來自「什麼時候用哪一個」。

值得一提的是，報導說 Goyal 在結尾給出了「什麼時候該用 Jev」的規則，但沒有展開。這是全文最明顯的缺口——對想落地的人來說，那幾條規則比演講金句更有價值。

四、UiPath：用呼叫次數換上下文長度

UiPath 的 Chibi Vikram 與 Kevin Bernstein 展示了一個很聰明的工程模式：錦標賽式 chunk 排序。做法不是把幾十份文件塞進一個大上下文讓模型一次判斷，而是分組、讓 Jev 在每一小組裡選出最相關的，勝者晉級，逐輪收斂。

結果是：數千次 Jev 呼叫，全程不到一秒。

「We realized that Jev is a building block that we can adjust, and we have to find these new strategies where we will be able to apply this building block. It might look less intelligent on its own, but with these strategies and patterns, we can get more intelligent — with even the current Jev model that we have.」 —— Chibi Vikram, UiPath

這段話值得拆開。它承認了單顆決策模型的局限：它單獨看可能不那麼聰明。但它同時指出了一條補償路徑：用演算法把「很多次小判斷」組合成「一次大判斷」。從複雜度看，這是把 O(n) 的注意力問題，拆成 O(log n) 的比較樹；從成本看，這是把「長上下文」換成「多次廉價呼叫」。

這個模式的適用邊界也很清楚：它適合可比較、可淘汰的任務（排序、檢索、候選收斂），不適合需要全局推理的任務（因果分析、多步規劃）。把錦標賽用在錯的任務上，只會得到一個很快的錯誤答案。

五、Workday：從預測下一個字，到預測下一個動作

Workday 的 Scott Roberts 展示的 demo 最短，但可能是最日常的：使用者在請假表單裡還在打字，介面已經開始自動填寫。

「From predicting what you want to say to predicting what you want to do.」 —— Scott Roberts, Workday

這句話是整場最好的產品總結。LLM 的範式是「預測下一個 token」；決策模型的範式是「預測下一個動作」。前者產出文字，後者產出狀態轉移：選哪個請假類型、填哪個日期、走哪條審批路徑、標記哪個欄位。這些判斷的延遲要求是毫秒級，因為它們發生在用戶輸入的間隙裡——超過 200 毫秒，使用者就會感覺到卡頓。

也正因為如此，這個場景幾乎不可能用推理型 LLM 做。不是因為 LLM 不聰明，而是因為它來不及。這一點解釋了為什麼 decision model 不是「更便宜的分類器」，而是一個新的互動原語。

六、場外的信號：一個與會者做的夢幻足球網站

報導裡有一個很容易被略過的小故事：作者旁邊坐著某公司的 AI 負責人，他用自己的時間，用 Jev 做了一個整理、排序夢幻足球新聞的網站。

這個故事的重要性不在「有趣」，而在它展示了決策模型的消費級形態：不是聊天，不是生成，而是「把一堆東西排序、分類、打分」。這類需求在過去要麼用規則硬編碼，要麼用一個昂貴的 LLM 呼叫；現在可以變成一個便宜的、可高頻呼叫的原語。當一個週末項目就能做到，通常意味著一波長尾應用正在路上。

七、被同一日發生的事改寫：Google 的 $0.10

這場演講發生在上午。下午，Google 發布了 Gemini Decision 1 與 Decisions API：支援 yes/no、多選、rubric 評分，單次請求最多 1,000 個問題、256K 上下文、255 個選項，接受文字、圖像、音頻、視頻、PDF，端到端 150–250ms，每個答案附 confidence，定價 $0.10 / 1M input tokens、輸出免費。

對照 Jev 的 $0.042 / 1M input，Google 貴了約 2.4 倍；但 Google 多給的是模態、上下文、與一個雲廠商的默認信任。更重要的是，Google 說這個項目原本是 DeepMind 的內部原型，約六週內由一個小團隊做成模型加 API。

這就是這場演講的歷史位置：它記錄了「system one 作為 TypeSafe 的賽道」的最後幾個小時。上午，Almeida 還在台上說要「automate everything」；下午，這個類別就變成了三大雲廠商之一的標準 API。

這不意味著 TypeSafe 輸了。恰恰相反，類別被商品化，通常意味著開創者已經證明市場存在。但它改變了護城河的形狀：模型本身不再稀缺，稀缺的是模式庫、工具鏈、與企業工作流的嵌合程度。UiPath 的錦標賽、Glean 的零樣本路由、Workday 的預填，這些都是「模式」，不是「模型」。它們可以被複製，但需要時間與場景知識。

八、獨立評測：66 分與 92.2% 之間

Google 自己的測試說，Decision 1 在 7 個共享 benchmark 中贏 Jev 1.14 五個，包括 JevBench 上 92.2% vs 90.0%。但 Artificial Analysis 的獨立結果是：Decision Index 66 分，與 Jev 1.14、Elephant 9B 並列，落後 Drex Max v1.1 與 GLiDE v1.2 七分。

這張表要這樣讀：Google 在輸入 token 上便宜 2.4 倍，在「完成一個任務」上卻貴 2.2 倍。 原因不是定價，是效率——它可能需要更多呼叫、更長上下文，才能得到同樣的答案。這正好印證了 Almeida 的架構主張：決策模型的成本，應該按「任務」算，不是按「token」算。

對買家的實務含義很簡單：不要用 $/token 比較決策模型。 用 $/task、延遲、與失敗成本。這三個數字加起來，才是部署決策。

九、這場報導沒有回答的問題
  • 錯誤率。 全文沒有給出具體準確率或失敗率。對生產環境來說，這是最關鍵的一頁。
  • Glean 的使用規則。 報導提到 Goyal 給了「何時用 Jev」的規則，但沒有展開。這是本文最大的信息缺口。
  • 校準。 Almeida 說每個答案都帶 confidence，但沒有說這個 confidence 在不同分佈下是否仍然可靠。Brier 分數 0.18 是 Decision 1 的，不是 Jev 的。
  • 樣本偏差。 這是 TypeSafe 主場的場次，上台的客戶都是成功案例。沒有失敗部署、沒有回退故事。
  • 與 LLM 的邊界。 三種模式都展示了「Jev + 其他模型」的混合，但沒有人給出「什麼時候不該用 Jev」的判準。
十、行業 insight：決策層的三個真正變化

第一，軟件的預設形態，從「一次大推理」變成「許多次小判斷」。 這不是成本優化，是架構重寫。當一次判斷只要幾毫秒，開發者會開始把判斷放進更多地方——表單、日誌、檢索、路由、審批。軟件的「智能」不再是某一個功能，而是無處不在的微小決策。

第二，護城河從模型移到模式。 當 Google 用六週把模型商品化，剩下的差異只能在「怎麼用」：錦標賽、推測式預填、零樣本路由、混合診斷。這些模式需要場景知識，而場景知識不會被一個 API 抹平。

第三，買方的語言變了。 Glean 說的不是「快 10 倍」，是「taxonomy 變化時不用重訓」。這是企業採購的真實痛點：分類體系會漂移。任何賣決策層的公司，都應該用這句話做定位，而不是用 benchmark。

「I think that there's going to be an explosion of what software can do, and we will want people to be exploring those boundaries of software. Not necessarily because it's valuable, but because they can, because we have new frontiers to explore, and this is what the early internet was like.」 —— Diogo Almeida, TypeSafe AI

這句話很浪漫，但也是這場演講最需要打折的一句。「早期互聯網」的類比，暗示了一個開放、無主、實驗成本極低的前沿。但決策層的現實是：它當天下午就被一個雲廠商定價、被一個框架日零支援、被一個 benchmark 口徑戰包圍。前沿是存在的，但它不屬於所有人。

十一、如果你星期一就要用
  1. 先找「高頻、低風險、可降級」的判斷點。 表單欄位、日誌分類、工具選擇、檢索淘汰——這些錯了可以回退，且呼叫量大。
  2. 用 $/task 做模型選擇，不用 $/token。 把「一次任務需要幾次呼叫、多少上下文」算進去。
  3. 把 confidence 當一等公民。 沒有信心分數的決策模型，不應該接進自動化流程。
  4. 先做路由，不要做替代。 Jev 處理簡單判斷，LLM 處理複雜推理；用一個 router 把兩者接起來，比換掉整個 stack 現實。
  5. 量度失敗，不只量度成功率。 錯誤是否可預測、是否可被護欄接住、是否會靜默傳播——這三個問題比準確率更重要。
