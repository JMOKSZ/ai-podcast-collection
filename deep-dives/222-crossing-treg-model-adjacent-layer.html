站在模型邊上——九個月三次轉型，Treg 點樣把自己縮成一層平台唔願意做的東西

📅 2026-10-19·🎙️ 楊遠騁（Koji）·👤 嘉賓：Jason Zhou（Treg 創辦人）、石天鑫（Treg Founding Engineer）

呢集表面係一個「四人團隊九個月轉型三次」嘅創業故事，實際上係一份應用層生存坐標系。當 Claude Code 同 Codex 由工具變成平台，做應用嘅人只剩兩條路：往上做厚，自己做 harness、記憶、沙盒、工作流，幻想成為新入口；或者往下做薄，只做一層平台唔願意做、但所有 Agent 都需要嘅東西。Treg 選咗後者——唔係因為佢更高尚，而係因為佢試過前者，差点死喺上面。

「未來六到十二個月，零人公司絕對唔係一個可能嘅情景。更需要解決嘅問題，大概係喺人和 Agent 大規模協作嘅情況下，你點樣做這件事。」 Jason Zhou，節目轉錄摘要回譯

一、為什麼呢集值得單獨寫

過去兩年，AI 應用層嘅默認動作係「往上做厚」。做一個產品，先自己搞定 harness，再搞定記憶，再搞定沙盒同權限，最後幻想自己會變成新嘅入口。呢個策略喺模型能力每年跳一代嘅環境裡，有一個致命問題：你花六個月建嘅護城河，可能係平台下個版本嘅默認功能。

Treg 嘅三次轉型，正好把呢件事拆到見骨。第一次，SuperDesign 被模型嘅前端能力追上；第二次，Coolant 被「增長冇通用解」打敗；第三次，佢哋唔再同平台競爭，而是把自己變成平台旁邊嘅一層基礎設施。呢個轉向唔浪漫，但它提供了一個可檢驗嘅命題：當智能本身變成公用事業，價值可能唔喺「更聰明」，而喺「更靠近交易發生的位置」。

另一個值得寫嘅原因，係嘉賓對「零人公司」嘅否定。2026 年下半年，幾乎所有 AI 創業者都在講「一個人加一堆 Agent 就可以運營一家公司」。Jason 同石天鑫真係花咗兩個月，唔做產品，只搭自動化 loop 去驗證。結論係：客服可以全自動，修 bug 可以全自動，但增長幾乎唔可以。呢個「實測之後嘅反潮流判斷」，比任何樂觀預言都更有參考價值。

階段產品做咩為何轉型
起點SuperDesign（Cursor 插件）設計 Agent，最初只係 Jason 為 Cursor 寫嘅週末插件開源幾個月自然長到 6,000+ GitHub stars，說服佢離職創業
第一次轉型SuperDesign（Web 版）由插件改成獨立 Web 產品，想觸達非 Cursor 用戶插件形態冇清晰變現路徑；模型前端能力由 Gemini 3 開始軍備競賽；用戶整體遷移到 Claude Code / Codex

留意呢條時間線嘅形狀：唔係「先有宏大願景，再一步步實現」，而係「每次都被現實推着走」。Jason 自己嘅講法係「每一次都是被逼的」。呢句話好重要，因為它解釋咗為什麼 Treg 嘅定位咁窄——窄唔係戰略選擇嘅結果，而係兩次失敗之後，被市場削出嚟嘅形狀。

三、第一次轉型：被兩頭夾擊的設計 Agent

SuperDesign 嘅起點非常典型：一個有設計內容受眾嘅 YouTuber，順手為 Cursor 寫咗個插件，開源之後幾個月累積 6,000 多顆星，全部自然增長。呢個數字說服 Jason 離職。但佢創業之後第一件事，就係放棄開源、轉做 Web 版，理由係插件冇清晰變現路徑，而且想觸達更多唔用 Cursor 嘅人。

事後佢承認呢個判斷係錯嘅。錯唔在於「Web 版唔應該做」，而在於佢低估咗平台遷移嘅速度：

「但我也沒想到，接下來一年所有人都湧向了 Codex 和 Claude。」 Jason Zhou，節目轉錄摘要回譯

呢句話揭示咗一個應用層常見嘅雙重擠壓：

  • 上游擠壓：模型本身嘅前端能力由 Gemini 3 開始進入軍備競賽。當模型可以直接生成高質量 UI，設計 Agent 嘅差異就被抹平。
  • 下游擠壓：用戶整體遷移到 Claude Code 同 Codex。插件形態唔再係一個獨立入口，而係平台生態裡嘅一個小零件。

兩邊一夾，SuperDesign 嘅位置就消失咗。呢個教訓唔係「設計 Agent 冇市場」，而係當你嘅核心價值可以被模型嘅一次版本更新吸收，你嘅產品就只係一個過渡態。

四、第二次轉型：Coolant 與「增長沒有通用解」

第二個產品 Coolant，目標係做全自動增長 Agent：幫已經有生意嘅公司做 SEO、社交媒體、廣告同客戶開發。靈感來自 Posia。Jason 喺 2026 年 2 月見到 Posia 時，佢嘅 ARR 大約十幾萬美元，但體驗「驚為天人」——註冊之後唔使填任何資料，Posia 淨係憑 email 就推斷出你係邊個、做咩，然後生成兩三個創業想法；你揀一個，它就直接幫你建落地頁、搵客戶、發 cold email，而且真係有人回覆。

但 Jason 真正做完之後，發現 Posia 最聰明嘅地方唔係技術，而係產品邊界：它賣嘅係「AI 幫你運營整間公司」嘅願景，但實際交付嘅只係 zero-to-one 階段——建網站、裝工具，做到極順；一旦進入真實業務、要交結果，難度就完全唔同。Coolant 想服務「已經有生意、想規模化」嘅創辦人，結果撞上同一堵牆，做咗大約一個月就停。

失敗嘅技術原因，Jason 歸納為兩點：

  1. 數據攞唔準。工具市場極度碎片化，每個場景有幾十家供應商，各有強項同價格。
  2. 增長依賴人嘅品味。營銷冇通用解，真正有效嘅渠道，往往係大量試錯之後嗰條「別人不做、但適合你」嘅路，然後加倍下注；但當所有人都做同一件事，渠道就失效。

佢用 SEO 舉例：畀 Agent 嘅工作流係抓關鍵詞、看流量與競爭、然後下注。真做落去才發現，大部分詞早就被廝殺過，真正嘅機會在於判斷「現在流量很低、但一到三個月後會起」嘅詞——呢一步 Agent 做不到。

增長嘅本質，係大量試錯之後找到那條別人不做、但適合你嘅渠道，然後加倍下注；當所有人都做同一件事時，渠道就失效。 本文對 Jason 論點嘅概括，非逐字引用

呢個判斷嘅殺傷力在於：它唔係講「Agent 未夠強」，而係講增長呢件事嘅結構，本身就唔適合被全自動化。因為增長需要嘅係「逆共識判斷」——喺數據未顯示之前，先押注一個別人不看好的方向。呢種判斷嘅本質係承擔不確定性，而 Agent 嘅設計目標恰恰係降低不確定性。

五、兩個月的「零人公司」實驗：哪些可以自動化，哪些不可以

Coolant 停咗之後，團隊冇即刻找下一個產品，而係花咗約兩個月，用 AI 去運營 SuperDesign。呢個實驗嘅設計好純粹：如果「零人公司」可行，咁用 AI 運營一個已經有產品、有流量、有收入嘅小生意，應該係最容易嘅場景。佢哋搭咗大量 loop，去測試客服、修 bug、內容、增長等環節。

結論分三層：

環節能否全自動原因
客服✅ 可以問題模式重複，答案可以從歷史對話檢索；出錯成本低。
修 bug✅ 可以有明確成功條件（測試通過、重現步驟消失），Agent 可以自己驗證。
安全與運維✅ 可以規則明確、監控長期在線；小 loop 比人更適合做重複巡檢。
增長❌ 幾乎不可以需要品味、逆共識判斷、承擔不確定性；例外太多，需要人介入。
創新❌ 不可以如果 loop 可以創新，「給我建一個創業公司」就應該直接成功。

呢個結論直接推翻了「零人公司」嘅時間表。Jason 嘅講法係六到十二個月內都唔可能，更需要解決嘅問題係「人同 Agent 大規模協作」。注意呢個判斷嘅邊界：佢冇否定 AI 可以大幅減少人力，只係否定「完全冇人」——差別在於，人由「執行者」變成「判斷者」同「例外處理者」。

節目口徑 團隊 4 人；創業 9 個月、3 次轉型；Coolant 只跑咗約 1 個月；過渡期有 2 個月完全不碰產品，只做自動化驗證。

呢兩個月嘅第二個收穫係意外嘅：佢哋做咗好多增長實驗，「全部都冇用」；真正改變增長曲線嘅，係石天鑫某日順手做嘅一個 Codex 插件。上線之後，增長曲線突然改變，大量用戶湧入，而且呢批用戶嘅流失率更低。呢件事直接指向第三次轉型。

六、第三次轉型：Treg——把「中繼層」抽出來單賣

嗰個插件嘅成功，幾乎冇技術含量：Codex 剛推出插件市場時，市場上冇乜有趣嘅插件，佢哋就把原本 Cursor 加 skill 嘅一套搬過去。因為 ChatGPT 同 Codex 本身有巨大用戶基數，插件好容易被注意到；只要產品吸引，就會被使用、被轉化。

最戲劇性嘅細節係排名規則：當時插件市場按字母排序，佢哋把名由 SuperDesign 改成「01 SuperDesign」，直接排第一。石天鑫話呢個位置只維持咗幾日，平台好快就換咗自己嘅排序邏輯，但呢個先發優勢帶嚟咗第一批啟動量。

「早期嘅工具同市場都值得試，因為你永遠唔知邊一次嘗試會帶嚟流量。」 石天鑫，節目轉錄摘要回譯

Jason 由呢件事抽出一個類比：Codex 同 Claude Code 而家有巨大用戶基數，但體驗唔夠好；喺佢哋周圍做體驗增量，就好似當年 Zynga 長喺 Facebook 上、PayPal 長喺 eBay 上。平台有巨大用戶、體驗又唔夠好，中間就一定有空間。

而 Coolant 時期真正可轉移嘅遺產，唔係任何一個 harness——事後看，嗰啲 harness 彼此差異唔大——而係中間嗰層「中繼服務」：做 GTM 或任何專業工作，都需要大量專業數據同工具。Treg 就係把呢層抽出來，獨立賣。

Jason 對 Treg 嘅定位係「數據與工具領域嘅 Open Router」：把分散在各家供應商嘅數據源同 API 整合起來，讓 Agent 用一條 key 就能調用。商業上按用量計費，冇月費。

節目口徑 Treg 上線約 3 週，收入已係 SuperDesign 嘅數倍（具體數字未披露）；純按用量收費，無月費。最集中嘅付費場景係 B2B 客戶開發，其次係 SEO／AEO 同社交媒體內容。
七、商業模式：Treg 更像 Costco，而不是批發商

面對「模型公司或頭部數據商為什麼唔直接接、要繞過中間層」嘅問題，Jason 嘅答案係：現實中冇單一頭部供應商。每個場景都有幾十家，各有強項同價格，企業需要多種資訊才能找到啱嘅一家。

石天鑫嘅類比係 Costco：站喺中立位置，替用戶篩選市場上最好嘅數據，以高性價比供貨。跨平台係另一層價值：即使你由 Claude Code 換到 Codex，之前累積嘅工具調用同數據仍然喺 Treg。

呢個定位嘅經濟學含義值得拆開：

  • 佢賣嘅係「選擇嘅成本節省」，唔係數據本身。客戶唔係買唔到數據，而係唔想逐家比較、逐家簽約、逐家維護 key。
  • 按用量計費，令價值同使用同步。冇月費，降低嘗試門檻；用得越多，Treg 抽成越多。
  • 中立性係賣點，亦係軟肋。如果平台自己開始做工具市場同計費，或者某個場景出現贏家通吃，中間層嘅空間就會被壓縮。

石天鑫仲提出一個觀察：未來各種 Agent harness 可能會因為「連接咗獨特嘅數據」而吸引用戶。佢舉例：有個朋友用 Kimi，因為它連接咗 Wind 嘅股票交易數據。呢個觀察同 Treg 嘅定位互相呼應——harness 本身會趨同，數據連接才係差異化。

八、「Agent 才是真正的用戶」——把評測主體換人

整集最有原創性嘅一點，係石天鑫對「用戶」嘅重新定義：

「我理解我們現在很多產品的真正用戶，其實不是那個人，而是那個人的 Agent——所以它對我們的產品有最直接、最真實的感受。」 石天鑫

呢句話聽起來像修辭，但它直接改變咗產品評測嘅方法。傳統 SaaS 靠人做 NPS、靠人寫 feedback；但當真正調用 API 嘅係 Agent，人嘅感受只係間接嘅。Treg 因此把評測主體由人換成 Agent：

  1. 隨機抽取用戶，讓其 Agent 給回饋。簡單 bug 直接修；有趣嘅功能請求就接受並評估。
  2. 對每一次 API 調用做脫敏評價。呢條數據有冇用？邊個字段起了作用？
  3. 累積成每個 endpoint 嘅兩張評分圖：「有用性」同「性價比」。
  4. 把評分展示給後來嘅 Agent，讓它按場景選擇：要精度就選最貴最好；要廣度同低價就選性價比高。

Jason 把呢個機制叫做 Treg 嘅數據飛輪，並認為它係應用層 AI 團隊嘅通用解法：既然你唔可以自己訓模型，就要讓某種數據回流到產品裡。

但呢個飛輪有一個未解嘅方法論問題：Agent 嘅「有用」評價，同最終人類用戶嘅「有价值」之間，係咩關係？如果 Agent 只係按「呢條數據幫我完成任務」評分，它可能會系統性偏好「容易用」而唔係「準確」；如果它按「成本效益」評分，又可能犧牲長尾場景嘅覆蓋。節目冇回答，但呢個問題會決定飛輪係真護城河，還係一個好聽嘅故事。

九、Loop Engineering：運營可以，創新不行

石天鑫引用《系統之美》嘅框架，認為公司係一個複雜系統，關鍵係開環與閉環回饋。佢嘅方法論非常具體：

  • 唔好一開始就建複雜嘅 loop。短而精更有用。
  • 一個 loop 只做一件事。一個只監控 DDoS 同安全風險；一個只做代碼清理；每次做嘅事小到很難出錯。
  • 建到十幾個之後，它們自然形成一個互相協調嘅複雜系統。當一個 loop 發現 bug 並報告，線上監控 loop 會發現並告警。

安全係佢舉嘅例：創業前佢從未想過要處理大量黑客攻擊，但只要產品有邀請新用戶、送 credits 之類嘅激勵機制，就會被持續攻擊；一個四人團隊每日花精力同呢件事糾纏，非常痛苦。一個長期監控風險行為、一發現小漏洞就補嘅 loop，可以省好多精力。

創新嘅部分唔可以交畀 loop，否則「給我建一個創業公司」就應該直接成功。 石天鑫，節目轉錄摘要回譯

呢個分工其實係對「Agent 取代人」嘅一個更精確版本：Agent 適合接管「目標明確、成功條件可驗證、例外有限」嘅工作；人應該保留「目標模糊、需要品味、例外無窮」嘅工作。大部分關於 AI 取代工作嘅爭論，都係因為冇做呢個區分。

十、人成為瓶頸：由 5–10 個 session 到 50–100 個

兩位嘉賓都話，而家同時跑嘅 session 遠比以前多。Jason 話 Fable 之後，佢基本同時跑五到十個 session，因為自完成嘅質量已經很高；另一個變化係由純本地轉向雲加本地混合，context 可以隨時交換。

石天鑫提到一個由 YouTube 資深工程師 Kun 做嘅工具 First Mate：船長只負責派任務畀大副，大副再同其他 coding session 溝通。佢冇直接用呢個項目，但學咗個概念，而家用 Herder 呢類新一代終端管理工具，讓 Agent 互相對話，或者由一個主 Agent 轉派任務。
