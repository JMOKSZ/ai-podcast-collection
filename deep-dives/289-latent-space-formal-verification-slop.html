「你的 code 第一次就能跑」——當形式驗證走出數學圈，四家公司如何把 Lean 變成結算層

〈The War Against Slop and an Emerging Weapon to Fight it: Formal Verification〉
出品：Latent Space·作者：swyx 團隊·核心受訪：Clark Barrett（&Truth 共同創辦人兼共同 CEO）
發布：2026-11-20 21:18 UTC·深度文章（非訪談）·約 9,200 字
來源：latent.space 原文全文；引語為原文直譯，英文原文附於引語後

2026 年 AI 圈的年度關鍵詞是「slop」——模型產出的低質代碼與內容。這個詞之所以流行，不是因為模型太差，而是因為模型看起來很對：語法正確、命名合理、註釋齊全，跑起來也不一定報錯。審查的人因此陷入一種新型疲勞——你不再對抗明顯的錯誤，而是對抗看起來沒問題的東西。

Latent Space 這篇文章的論點很簡單：對抗 slop 的下一件武器，不是更好的模型，而是數學證明。形式驗證（formal verification）用邏輯與證明來確認軟件／硬件的正確性；隨着 AI 解數學題的能力暴漲，它正從學術 niche 變成可用的工程工具。

文章走訪了四家公司——Harmonic、Theorem、Axiom Math、&Truth——但真正的骨架來自一個人：Clark Barrett，&Truth 共同創辦人兼共同 CEO、史丹佛計算機科學 Corbel Professor（Research），以及 cvc5 的共同創造者。cvc5 是當今最流行的 SMT（satisfiability modulo theories）求解器之一；用他自己的話說：

「很高興看到我的工具從實驗室裏的一個好主意，變成 cvc5 現在每天在 Amazon 的生產管線被呼叫數十億次。」 — Clark Barrett（原文："It's been fun to see my tools go from a good idea in the lab to cvc5 is now called billions of times a day in production pipelines at Amazon."）

以下我按四條線重構這篇文章：測試與驗證的差別、SMT 與 Lean 的分工、四家公司的路線分化、以及成本曲線正在怎麼改寫這件事的商業意義。

一、測試與驗證：差別在「你怎麼知道做完了」

當 AI coding agent 公司說自己「驗證」了工作，通常指的是三件事：agent 跑測試、agent 批評自己的輸出、或者另一個模型來當評審。Barrett 被問到這距離真正的驗證有多遠，他的回答是整篇最值得記住的一句：

「主要的分別，就是你怎麼知道你做完了。如果你在做測試、打補丁、掃描——用盡所有現有工具——它們相當好。它們找到一大堆問題。但你永遠不太確定：我是把它們全找到了，還是有一個正潛伏在那裏、我的工具抓不到？」 — Clark Barrett（原文："The main difference is really just, how do you know when you're done… you're never quite sure, did I find all of them or is there one more lurking there that my tool can't find?"）

這句話把「驗證」從一個技術詞選變成了認識論問題。測試給你的是抽樣信心：我試了這些輸入，都通過。形式驗證給你的是封閉答案：對所有合法輸入，這個性質成立——或者，這是一個反例。

兩者的差別在風險管理上很具體。測試的覆蓋率是一個機率陳述，而機率陳述在對抗性環境裏會失效：攻擊者不需要通過你的測試，他只需要找到你沒測的那一條路。形式驗證的承諾則是「不存在這條路」——前提是你指定的性質（property）本身是對的。這一點很重要，後面會回來談。

關鍵區分 測試問的是「我有沒有找到錯」；驗證問的是「能不能證明沒有錯」。前者是搜尋，後者是判定。AI 讓搜尋變便宜，但沒有讓判定變便宜——直到現在。

二、cvc5 與 SMT：不太會「想」，但很會「判」

要理解這個產業，得先分清兩個常被混用的東西：SMT 求解器與證明助手。

cvc5 是 SMT 求解器。它不負責「想出」證明，而負責在給定邏輯理論下判定一個公式是否可滿足（satisfiable）。實務上，工程師把規格形式化之後，求解器自動搜索反例或證明。它是一個判定程序（decision procedure），強項是封閉世界裏的組合爆炸。

Lean 則是證明助手（proof assistant）。你（或 AI）寫出證明，Lean 逐步檢查每一步是否合法。它不替你找路，但它保證你走的每一步都沒有作弊。用 Barrett 的話說：

「Lean 做的事，就是檢查你有沒有弄錯。你可以把它想成一個非常精密、專門檢查數學的檢查器。」 — Clark Barrett（原文："What Lean does is it just checks that you didn't make a mistake. So you can think of it as a very sophisticated checker for mathematics."）

這個分工解釋了為什麼 AI 與形式驗證是協作而不是取代：LLM 負責生成候選證明與規格草稿（搜索空間），求解器負責判定（剪枝），Lean 負責逐步核對（結算）。三者接起來，才是一條完整的生產線。

也解釋了為什麼 cvc5 能工業化。Amazon 的用法不是「證明整個系統正確」，而是把它塞進具體環節：Kiro（Amazon 的 agentic 開發環境）用它做規格分析與測試生成。這是形式方法幾十年來最現實的落地方式——不是一次證明全部，而是把判定能力嵌入每一個小決策點。

三、四家公司，四種賣法

文章把當前的競爭格局拆得很清楚。四家公司的共同點是都把 Lean 當結算層，差異在賣給誰、賣什麼。

公司產品核心賣點主要客戶場景
&Truth&Atlas（全球開源碼地圖，由 C 起步）、verification machine讀懂任何語言的 code，證明它滿足精確陳述的需求；讓人不必逐行理解也能信任記憶體安全、供應鏈審計
HarmonicAristotle（自動定理證明器）AI 寫證明、Lean 逐步檢查，結果不依賴 AI 正確數學、形式化研究
Axiom MathAxiomProver + AXLE生成 Lean 證明，並把證明嘗試回饋成訓練信號數學推理、模型自我改進
Theorem企業級驗證「Verification is the only defense that holds while adversaries scale.」安全、合規

Harmonic 的產品承諾寫得最清楚，也最值得抄下來當判準：

「在 Aristotle 內部，AI 寫證明，Lean 檢查每一步，所以一個結果永遠不會建立在『AI 是對的』之上。」 — Harmonic 官網（文章引用）

這句話是整個產業的信任架構。它把「AI 可能幻覺」這個風險，轉移到一個不依賴 AI 的檢查器上。你可以不信任模型，但仍然信任結論——因為結論的每一步都被一個獨立的、可審計的程式核對過。

Axiom 的路線更進一步：形式驗證不只是防守，也是訓練信號。證明嘗試成功或失敗，反過來改進下一代模型。Axiom CEO Carina Hong 在六月接受 Latent Space 訪問時說得更直白：

「形式驗證、verified AI，對我們而言不只是處理或踢掉那些爛東西、幻覺、錯誤。它是要放大才華。它是要通往超智慧。」 — Carina Hong（原文："Formal verification, or verified AI, to us it's not just about handling or kicking out the lousiness, the hallucinations, the mistakes. It's about scaling brilliance. It's about super-intelligence."）

&Truth 則選擇了最重的一條路：先建地圖。&Atlas 的定位是「世界開源碼的地圖，由 C 語言起步」。為什麼是 C？因為記憶體安全問題在 C 裏最密集、後果最嚴重，而且存量最大。Barrett 描述最終目標：

「我們技術的一個非常強大的用法，是掃過全世界所有 C code，無論開源或閉源，確認它是記憶體安全的。如果不安全，我們可以指出：這段 code 這裏有問題，你必須修。」 — Clark Barrett（原文："One really powerful use case for our technology is going through all the C code in the world… and trying to ensure that it's memory safe."）

這是一個典型的「基礎設施先行」策略：不賣單點工具，先建一張所有人都會查詢的地圖。如果成功，它會成為一個收費站——不是因為它擁有 code，而是因為它擁有關於 code 的判定。

四、成本曲線：從 token 昂貴到 token 高效

形式驗證過去幾十年推不動，原因不只是難，而是貴。寫規格需要受過訓練的人，證明需要專家，維護需要持續投入。AI 改變的第一件事是生成成本；第二件事，是讓「驗證」本身變得 token 高效。

文章引用的一組數字很關鍵：在 36 個小型驗證任務上，Anthropic 報告 Opus 5.5 達到 50% 解題率，比 Opus 5 少用約 40% token。趨勢預期會延續，因為更多模型開始「在長時程驗證任務上受訓」。

成本 同一解題率下，token 消耗一年內下降 40%。若此趨勢延續，單位驗證成本可能再降一個數量級——經濟門檻由「關鍵系統專用」下降到「CI 可默認開啟」。

把這兩個數字放在一起看，會得到一個比「AI 會寫證明」更重要的結論：驗證正在從資本支出變成營運支出。過去你要養一個形式方法團隊；現在你可以在 CI 裏掛一個默認步驟。這個轉變對採用曲線的影響，遠大於任何單一 benchmark 的進步。

當然，50% 解題率意味着還有一半失敗。而且「小型驗證任務」這個描述留下了很大的解釋空間：任務分佈是什麼？失敗的是最難的還是最無聊的？36 個樣本夠不夠？文章沒有回答，這是需要保留的疑問。

五、veri-coding：從寫 code 到寫規格

文章最後回到開發者體驗。&Truth 官網提出一個對比：從 vibe-coding 到 veri-coding——驗證層成為工作流的一部分，而不是事後審計。

Barrett 描述的使用體驗值得完整引用：

「如果你把驗證機器接上你的 agent，你仍然可以說：『嘿，我要你建這個。』也許需要一點功夫，跟 agent 把你要建的東西的規格真正定下來。但之後 agent 可以在底層與形式工具協作，而你看到的幾乎沒什麼不同——除了你的 code 第一次就能跑。」 — Clark Barrett（原文："…essentially what you'll see is almost no difference except your code will work the first time."）

「第一次就能跑」是一句很聰明的產品語言。它沒有承諾「不用改」，而是承諾「不用除錯」。對一個被 AI 生成代碼淹沒的工程師來說，這個差別就是一天。

更深的變化在於人的時間分配。如果 agent 負責寫 code、驗證機器負責檢查，那麼人的工作會從寫 code／審 code轉移到寫規格／審規格。這是軟件工程史上的一次槓桿轉移：從「實現細節的正確」轉向「意圖表達的正確」。

六、outcome engineering：誰卡住 agent 時代的收費站

文章結尾引用了一條 tweet，來自 Cognition 的開發者關係負責人 Nader Dabit。它的邏輯很簡單：當你只告訴 agent 團隊「我要這個」、它們自己蓋完，人類唯一剩下的工作就是檢查交付物是否正確。

Latent Space 把這稱為「outcome engineering」——不論這個詞會不會流行，它指向的方向是清楚的：當生成變便宜，驗證就變成瓶頸，也變成價值捕獲點。

這與本週另一條主線（Anthropic 的 IPO 定價）形成互補。市場買的是可信度，不只是 benchmark 分數。如果驗證層成熟，模型能力差距會被「可驗證性」重新定價——能產出可被機器檢查的輸出的模型，比「看起來很強」的模型更有商業價值。

一層更冷靜的推論：如果驗證成為默認步驟，那麼「模型出錯」的社會成本會下降，但「規格寫錯」的成本會上升。因為機器會忠實地證明你說的東西，包括你沒想清楚的部分。形式驗證消滅的是實作 bug，不是需求 bug。

七、安全：最大的商業場景，也是最難的承諾

文章把網絡安全放在很重要的位置。Barrett 明確說，&Truth 的重點之一是掃過全世界的 C code，確認記憶體安全。Theorem 的口號則直接把對抗性寫進產品定位：

「當對手規模化，驗證是唯一守得住的防禦。」 — Theorem 官網（原文："Verification is the only defense that holds while adversaries scale."）

這句話的邏輯值得拆開。傳統防禦（簽名、掃描、模糊測試）的成本曲線跟攻擊者規模掛鈎：對手越多，你越需要更多規則、更多樣本、更多人力。形式驗證的成本曲線則與系統複雜度掛鈎，與對手數量無關。一旦證明成立，它對一萬個攻擊者和一個攻擊者同樣有效。

但這裡有一個未被充分討論的張力：如果驗證器本身也是 AI 生成的一部分，我們只是把信任轉移到另一個模型上嗎？Harmonic 的答案是否定的——Lean 是獨立的檢查器，不依賴 AI。但整條管線的其他環節（規格生成、 proof 搜索策略、失敗時的重試）仍然大量使用模型。信任的邊界在哪裡，取決於你把哪一段放進 TCB（trusted computing base）。

八、生態比文章標題更寬：Lean 不是唯一

一個容易被忽略的細節：Anthropic 那張「from code to a machine-checked guarantee」示意圖，用的是 Rocq（前 Coq），而不是 Lean。這說明生態並非只有 Lean 一家；Lean 的優勢是社群動能與數學形式化的規模，但在工業驗證領域，Rocq、Isabelle、TLA+ 各有地盤。

文章也提到兩個規模數字，值得放在一起看：

  • Vals 認為 GPT-6.2 Astra 產出了首個 Smoktunowicz Gap Theorem 的 Lean 證明。
  • Anthropic 用 Lean 形式化費馬最後定理，專案規模 1,300 萬行。

1,300 萬行是一個什麼概念？它比很多作業系統的核心還大。這說明形式化的瓶頸不只是智力，還有工程規模：把一個已知證明翻譯成機器可檢查的形式，本身是一個巨大的軟件工程項目。AI 在這裏的價值可能不是「想出證明」，而是「搬運與補洞」——把人類已經知道的數學，變成機器可以結算的資產。

九、行業 insight：驗證層是 agent 時代的結算層

把四家公司放在一起看，會發現一個共同的結構：它們都不賣「更聰明的模型」，它們賣「可以被信任的判定」。

這是因為 agent 經濟的核心問題不是生成，而是授權。你願意讓一個 agent 直接改 production 嗎？你願意讓它提交 PR 嗎？你願意讓它管預算嗎？這些問題的答案不取決於模型多強，而取決於失敗時誰能發現、誰能證明。驗證層提供的就是這個：一個不依賴模型自我報告的失敗檢測機制。

從這個角度看，文章標題裡的「war against slop」其實是一場信任基礎設施的建設。Slop 不是品質問題，是可核查性問題：當產出速度快過人類審查速度，唯一的出路是讓機器去做機器能做的檢查。

十、前後脈絡：這條線埋了半年

與 Axiom 的六月訪談。Carina Hong 當時提出「scaling brilliance」，把形式驗證從防守工具提升為能力放大器。這篇文章是把當時的口號落地成產品地圖：&Atlas 之於 &Truth、Aristotle 之於 Harmonic、AxiomProver + AXLE 之於 Axiom、企業驗證之於 Theorem。

與 Dwarkesh〈The avalanche that hit math〉（11-13）。數學能力外溢到 code 驗證，是 RSI 敘事中最可測量的一條支線——不同於模糊的「AGI 將至」，這裏有 50% 解題率、40% token 降幅、1,300 萬行形式化等硬指標。

與 Linear 的 GTM（287）。一個賣「人被調用的地方」，一個賣「機器被信任的地方」。兩者其實是同一條價值鏈的兩端：agent 做了更多工作之後，人類保留的兩個位置是決定要做什麼（規格）與確認做對了（驗證）。

與 Tomasello 的代理性（288）。那集說代理性的核心是「知道自己在做什麼」與「能被問責」。形式驗證給出的，正是一個可以被問責的機器介面：不是「我相信它」，而是「這裡有一份可檢查的證明」。

十一、爭議點與未解問題

  • 50% 解題率是「小型任務」。文章沒有披露任務分佈、失敗模式、以及「小型」的定義。從 50% 到生產可用，中間可能還有一個數量級的工程差距。
  • 規格才是真正的地獄。形式驗證只能證明「實作符合規格」。如果規格寫錯，你會得到一個被證明的錯誤系統。Barrett 自己也承認，使用者需要花功夫「跟 agent 把規格真正定下來」。這部分的工作量被文章低估了。
  • 信任邊界沒有說清。整條管線中，哪些部分被形式化、哪些部分依賴模型判斷？如果規格由模型起草、proof 由模型搜索、只有最後一步用 Lean 檢查，那麼 TCB 其實比宣傳的大。
  • &Atlas 的商業模式未明。「世界 code 的地圖」聽起來像公共基礎設施，但它是一家公司。誰付費、付多少、資料如何更新，文章沒有回答。
  • 形式驗證不處理「意圖」。它可以證明你沒有寫出 buffer overflow，但不能證明這個功能應該存在。slop 的一大部分不是 bug，而是做了不該做的事——這一層仍然需要人。

結語

這篇文章最有力的地方，不是它介紹了四家公司，而是它把一個抽象的哲學問題變成了採購問題：你願意為「知道做完了」付多少錢？

測試文化的答案是「支付抽樣成本」；形式驗證的答案是「支付證明成本」。過去證明的成本高到只有核電、航天、晶片設計付得起；現在 AI 把生成與搜索的成本壓下來，證明開始進入 CI 的預算表。

如果這個趨勢成立，未來幾年的軟件工程會出現一個新的分層：上面是意圖（規格），下面是實作（code），中間是結算（驗證）。模型可以在下面兩層之間來回，但中間那層必須獨立、可審計、不依賴模型的自我報告。

「你會看到的幾乎沒什麼不同——除了你的 code 第一次就能跑。」 — Clark Barrett，論 veri-coding 的使用體驗

這句話聽起來像營銷，但它其實是一個很深的承諾：軟件工程的重心，從「除錯」移到「表達」。而當表達成為瓶頸，寫得清楚的人——不是寫得快的人——會重新變得稀缺。
