Latent Space （swyx + Alessio Fanelli）

Can a Cloud-Native Harness Make Agents Reliable Beyond the Desktop? 訪談 發布：2026-10-07 14:10:45 UTC（HKT 22:10）｜ 受訪：Craig McLuckie、Joe Beda（Stacklok；Kubernetes 共同創造者）｜ 作者：Richard MacManus

主題

把 coding agent 的 harness（代理外殼）由桌面搬到雲端，並用 Kubernetes 式的「控制迴圈」思維重新設計——令 agent 成為企業可集中管治、可暫停、可審計的基礎設施，而非綁死在個人筆記本上的工具。

嘉賓背景
  • Craig McLuckie 與 Joe Beda 是 Kubernetes 的共同創造者（Google 出身），K8s 於 2014 年開源後成為容器編排的事實標準，開啟「cloud native（雲原生）」時代。
  • 二人於 2023 年創辦 Stacklok，獲 1,750 萬美元 A 輪（Accel、Madrona、Bain Capital）。公司最初做軟件供應鏈安全，近期轉向基於 Kubernetes 的 agentic 方案。
  • 核心產品：Mecatl（「cloud-native harness」，今年 6 月起以 GitHub 開源項目推出；名字是阿茲特克語「繩／索」，讀作 MEH-kah-tl，作者笑言初時誤以為在玩 K8s「cattle vs pets」的梗）、ToolHive（跑同管治 MCP server 的開源平台）、以及尚未開源的 AI Gateway。
  • 作者 Richard MacManus 指出：OpenAI 與 Anthropic 自 2025 年起都嘗試把 harness 推向雲端，「但成效參差」——難點在於 session 可靠性、工具執行隔離、上下文保留。
核心論點
  • ① Coding agent 的基礎架構天生「在地」：LLM 在迴圈中呼叫工具、帶著上下文前進；因為本地最易實作，多數 coding agent 都先做終端工具、再做桌面 App（文中舉例：Claude Code 最初就是 CLI 工具）。但「開著的筆記本」meme 正好說明——harness 一旦無法在雲端受管，就有結構性限制。
  • ② 雲端化的本質是把價值所在由桌面移到雲端。McLuckie 說這是「moving the locus of value from the desktop to the cloud」；Beda 補一句關鍵：「That's where the IP sits.」（IP 就坐在那裡。）代碼與上下文多源自本地環境，一旦留在桌面就極難納入管理。
  • ③ 應該追問架構的第一性問題。McLuckie：「為甚麼 agent loop 同 tool-calling 子系統綁得如此死？為甚麼 agent 身份係透過『人類身份系統』嘅視角去推理？」——即：agent 的迴圈、工具、身份，本應解耦。
  • ④ 桌面優先方案的硬傷：Beda 指桌面 harness 的 loop、本地執行、session state 往往生在同一個 process 內，「就算有可插拔性，架構仍然係一個（或一組緊密耦合的）process，係為桌面而設」。單純「lift and shift」（用 VM／容器／沙盒搬上雲）會引發 agent 生命週期問題，尤其係quiesce（在等待人類輸入時安全暫停）。
  • ⑤ Mecatl 的解法——把四樣東西各自獨立：agent loop 脫離 client、model provider、state store、execution environment；loop 與「敏感操作」（tool calling、bash）分離；session 管理與記憶亦分離，不再是躺在磁碟上的 JSONL 檔，而是原生進入可管理系統。Beda：「這是我們知道如何在雲端跑好的應用……把它抽出嚟，同更敏感嘅操作（tool calling、bash）分開，亦把 session／記憶分開。」
  • ⑥ 企業類比：像管 email 一樣管 agent。Beda：「我們認為，未來你為企業工作時同 agent 嘅互動，屬於該企業；佢哋會想管理、管治佢，就好似管 email 咁。」——此為由單人本地 harness，擴展為企業可中央運營的基建。
  • ⑦ 動機：降低對前沿實驗室／超大雲廠的依賴。McLuckie 明言，就像 K8s 幫企業降低對大雲廠的依賴一樣，Stacklok 要幫大企業減少對 Codex、Claude Code、GitHub Copilot 的依賴。「cloud native」對佢嚟講代表「喺一個同雲廠商細節解耦嘅雲上面跑」——同當年 K8s 時代差唔多。
  • ⑧ 現成 agent 工具係為個人／細團隊而設，企業規模唔啱用。Beda：「我哋同大型機構傾，佢哋掙扎緊：一件為六人團隊而設嘅嘢，點樣部署去幾千、甚至幾萬人嘅工程部隊？」
  • ⑨ 模型路由應該留在 harness 內。Stacklok 的 AI Gateway 唔按任務選模型（同 Glean 相反），只做存取控制、預算、報告、供應商路由。McLuckie：「我哋傾向見到語義路由嘅模型選擇，發生喺 harness 內一個 honed（調校好）嘅智能系統度，因為嗰度上下文更多。」
  • ⑩ 商業模式＝開源＋企業控制面。ToolHive 與 Mecatl 各自獨立可用；商用產品係「enterprise spine」——把兩者綁埋一齊的控制面，提供一致的身份、授權、政策、審計。
關鍵數據
  • Stacklok A 輪 1,750 萬美元（2023；Accel、Madrona、Bain Capital）。
  • Mecatl 於 2025 年 6 月以開源項目（GitHub：stacklok/mecatl）啟動。
  • ToolHive 最初在桌面用 Docker 容器管 MCP server，後擴展成 Kubernetes 網關＋註冊表＋operator helper。
  • 文中引 Stacklok 對 520 位「負責組織 LLM／agent 應用」領導者的調查（《State of AI Architecture 2026》）。
  • 對比時間線：Amazon S3／EC2（2006）→ 企業方案（如 Windows Azure）數年後才成熟 → Kubernetes（2014）→ 如今 agent harness 被期待重演同一曲線。
  • 客戶主要在受監管行業：McLuckie 指「大多係銀行、半導體公司、電訊商」。
重點引用

「我哋想，未來你為企業工作時同 agent 嘅互動，屬於嗰間企業；佢哋會想管理、管治佢，就好似佢哋管 email 咁。」

“We think, in the future, interactions that you have with an agent while you’re working for an enterprise belong to that enterprise; and they’re going to want to manage that and govern that like they do email.” — Joe Beda

「嗰度（本地環境）就係 IP 所在。如果你想真真正正把它納入管理，佢坐喺桌面就困難得多。」

“That’s where the IP sits. And if you want to be able to actually bring that under management, it’s that much more difficult when it’s sitting on a desktop.” — Joe Beda

「為甚麼 agent loop 同 tool-calling 子系統綁得如此複雜？為甚麼 agent 身份要用『人類身份系統』嘅視角去推理？」

“Why is the agent loop so intricately coupled to the tool calling subsystems? Why is agent identity being reasoned about through the lens of human identity systems?” — Craig McLuckie

「呢個領域有一大堆方案，但佢哋全部都基本上係為喺桌面跑而設。」

“There are a ton of solutions in this space, but they’re all focused to essentially run on the desktop.” — Joe Beda

「我哋嘅商業產品係『企業脊柱』——把兩者綁埋一齊嘅控制面。」

“Our commercial product is the enterprise spine, the control plane that ties them all together.” — Craig McLuckie
技術詳情
  • Mecatl 架構：agent loop 獨立於 client／模型供應商／state store／執行環境；工具執行與 bash 隔離；session 與記憶由磁碟 JSONL 改為可管理系統原生儲存。核心可歸為：loop 抽出 → 敏感操作隔離 → 狀態外部化。
  • ToolHive：開源管理 MCP server；由桌面 Docker → K8s 網關／註冊表／operator，處理 MCP 的輸入輸出授權。
  • AI Gateway：存取控制、預算、報告、供應商路由；不做語義／任務級模型選擇（刻意，讓路由留在 harness）。
  • Quiescing：確立 agent 生命週期可控——可在等待人類輸入時安全暫停，這是「lift and shift」做不到的關鍵。
  • 文中亦對照現有開源 harness 生態：Pi（minimal agent harness；Flue 等項目建基於此）——Beda 未點名，但強調其架構仍屬桌面優先。
行業 insight
  • K8s 曲線正在 agent 領域重演：2006 年起雲（S3/EC2）先由新創／個人用 → 數年後企業方案成熟 → 2014 K8s 規模化管理容器。作者認為 agentic 技術正走同一條路：企業唔想員工自訂開源 harness，亦唔想佢哋跑前沿實驗室「喺自己電腦度」的 harness。
  • 管治＝新的護城河：當 agent 互動被視為企業資產（IP），身份、授權、政策、審計就成為可收費的「控制面」——這是開源底層＋商用控制面的典型商業結構。
  • 與前沿實驗室 harness 的正面競爭：Stacklok 的市場定位——降低企業對 Codex／Claude Code／Copilot 的依賴——直接瞄準前沿實驗室把 harness 當鎖客工具的企圖。
前後脈絡

此訪談接續 Latent Space 近期對 agent harness 生態的連串報導：Pi（極簡 harness）與 Flue（建基於 Pi）、Glean 的模型路由方案（Stacklok 刻意走相反路線：路由留在 harness 而非網關），以及前幾輪對「harness 工程」與「企業自建 harness」的反覆討論。作者 Richard MacManus 的框架是把 agent harness 放進 K8s 的歷史類比中，屬「新聞＋訪談」的混合體。

爭議點

沒有尖銳對立，但有一條清楚的賭注：企業不應把 harness 交給前沿實驗室或個人桌面，而應自建雲原生控制面。這與「用 Claude Code／Codex 就好」的主流企業實務相衝——誰掌握 loop 與 session，誰就掌握 agent 的 IP 與管治權。

The Cognitive Revolution （Nathan Labenz）

Software That Never Breaks: OutSystems CEO Woodson Martin on Building Enterprise-Grade Apps at AI Speed 訪談 發布：2026-10-07 17:00:00 UTC（HKT 10-08 01:00）｜ 受訪：Woodson Martin（OutSystems CEO）｜ 主持：Nathan Labenz｜ 長度約 1 小時 9 分

主題

在 AI 寫代碼的時代，企業軟件如何既「快」又「永遠唔壞」（never breaks）。核心是 model-driven、確定性代碼生成：agent 改抽象模型、由系統生成代碼；並由此延伸至 token 支出、模型選擇、合規積壓、安全與人材策略。

嘉賓背景
  • Woodson Martin 於 2025 年 5 月出任 OutSystems CEO，接替創辦人 Paulo Rosado（掌舵逾 24 年）。此前在 Salesforce 任職 18 年。
  • OutSystems 於 2001 年創立，是企業級低代碼／應用開發平台，客戶包括 Petrobras、Vodafone、Toyota 等大型機構，以及 Axos Bank、YESCO；旗艦 AI 產品為 Mentor。
  • 節目由 Nathan Labenz 主持；本集為 OutSystems 贊助集（ad sponsor）。
核心論點
  • ① 創辦理念恰好對上 AI 時代：Rosado 2001 年的目標是「快速可靠地建自訂企業軟件」——「evolve software at the pace of the business without breaking anything」。Martin 認為，當 AI agent 承擔大部分建造工作，「never breaks」這部分比以往更重要。
  • ② 用「中間抽象層」換取可靠性：無論開發者用 Claude Code、Codex，抑或 OutSystems 自家 Mentor，agent 編輯的是「應用應該做甚麼」的抽象模型，而非裸代碼；再由系統確定性地生成代碼，內建安全、角色型存取控制（RBAC）與既有合規組件複用。這正是「vibe-coded 軟件成日壞」的解藥。
  • ③ 在位者的「已成熟 primitives」反而係優勢：Nathan 觀察到一個模式——已有成熟元件的在位者，加一層 AI 往往比 AI-native 新創重建硬骨頭更容易。Martin 同意，並補第二個優勢：與受監管客戶多年建立的信任，「無論你技術幾咁型」都好難由新創賺返。
  • ④ 「enterprise-ready」今日係乜：SLAs 仍重要但只佔一小部分。Martin 描述有客戶的 agentic 系統已完成，卻卡在合規積壓——等審批底層模型，包括「訓練數據是否合法取得」的問題；即使工作只是「由 PDF 抽出結構化數據」亦然。這種審慎一部分係組織僵化，但多數係合理：企業在 IT 資源分配上可承受更多風險，但在可審計、可爭議的決策（如貸款審批）上不行。
  • ⑤ AI 保險（AIUC）暫無 uptake：Nathan 問 AI 保險會否加速採用，並提及他早前報導過的 AIUC。Martin 覺得概念有趣，但指 OutSystems 客戶中暫未見採用。
  • ⑥ 安全＝修復速度：建基於共享平台 primitives 的組合，可以「一次修補、處處修好」；幾百個各自為政、用 AI 生成在自己 stack 上的系統則不能。Martin 強調「冇終點線」：COBOL、AS/400、Lotus Notes 系統仍然遍地，模型公司會同時從攻擊與防禦兩邊獲利。
  • ⑦ Token 支出的真實會計：在「把一切都轉向 AI」之後，出貨速度急升（見下）；token 支出在 6 至 7 月見頂，如今已低於預測。省錢來自：為自家工程團隊量身訂造的 harness＋LLM router（把例行工作導向更便宜的模型）。
  • ⑧ 反前沿模型敘事：Martin 的 broader claim——大部分企業 workload 唔需要 frontier model，有啲甚至唔需要模型。這也正是他要賣「易換模型平台」的理由。中國模型方面，他透露部分客戶有跑（蒸餾版或 post-train 版），主要為慳錢；又指其客戶有一半在歐洲，美國以外不少公司「不太想將數據交託美國公司」。
  • ⑨ 資深平台能讓「非熟練建造者」安全地做出幾乎任何東西：OutSystems 在此問題上做了 25 年。實例：你在亞洲幾乎任何地方銀行開戶，你的手機銀行 App 可能就跑在 OutSystems 上；鹿特丹的燃油終端系統亦係——確保柴油唔會流經一條上次裝過煤油的管道。
  • ⑩ 積壓（backlog）的兩種變化：①長年被詛咒的遺留系統現代化終於發生，有客戶把「一件六年嘅事」壓縮成六個月；②員工自建 dashboard 之後，新的積壓變成整合與標準化。Axos Bank、YESCO 報告大幅生產力提升，但 Martin 提醒生產力要一段時間才反映到 P&L。
  • ⑪ Mentor 的演進與「該建乜」難題：Mentor 由 2018 年的機器學習項目起步，如今是一組 MCP 服務（OutSystems remote MCP plugins），任何 coding agent 都能用。在他看來最難的問題仍是「該建乜」。OutSystems 的答案是一個新 agent：讀取客戶現有應用的 telemetry → 建議哪些流程 agentify → 預測 ROI → 生成第一版。
  • ⑫ 介面未來：App 會縮成對話中的 widget：Martin 預期一年後自己手機上仍有 100+ 個 App，但很多軟件會縮成「出現在對話中的 widget」。他舉 OutSystems 6 月 ONE 大會的 demo：一個貸款申請由 Claude 對話移入銀行手機 App。
