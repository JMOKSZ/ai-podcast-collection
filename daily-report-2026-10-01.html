英文播客

Latent Space （主播：swyx + Vibhu；嘉賓：Ari Weinstein、Nikunj Handa，OpenAI）

OpenAI DevDay 2026 特輯：Computer Use「180 度不同」，與 OpenAI 如何一週克隆 Jev 發布：2026-09-30 22:23 UTC（北京 10/1 06:23）｜片長約 40 分鐘

嘉賓背景

Ari Weinstein——OpenAI Computer Use 產品與工程負責人。職涯主線是「電腦自動化」：Apple（Shortcuts）→ 創辦 Sky（後被 OpenAI 收購，即如今 Codex Computer Use 的技術來源）→ OpenAI。Nikunj Handa——OpenAI API 產品負責人，入職約三年，前 Stripe，長期負責模型能力 API 化。主持人為 swyx 與 Vibhu。

核心論點
  • 「Computer Use 已 180 度不同」：Ari 直接回應 Dwarkesh 早前「Computer Use 兩年沒進展」的說法。關鍵變化有三——① 代理很會 debug 與自我恢復（過去能開頭，遇到問題就卡死）；② Computer Use 現在會寫 JavaScript 一次執行多步，不再一步一截圖；③ 多模態介面並用：截圖 + 無障礙樹（accessibility）+ DOM + Playwright，按任務切換。
  • 從「比人快」到「字面超人」：Ari 稱 Computer Use 現在在多數情境下已比普通人更快完成任務；下一個前沿是「literally superhuman」——比專家更快用軟件，屆時才能支撐真正的即時產品。
  • 瓶頸正在從模型轉向「世界本身」：代理越快，越被「操作本身的耗時」卡住。例如自動化 doordash.com 時，大量時間其實是在等網站載入；理想是 event-driven（JS load event），但有些事件本質上無法事件驅動，這是「一門統計科學」。
  • App Shots 的本質不是截圖：Ari 強調 App Shot 會帶入完整脈絡——連結指向、被截斷的日曆標題、無障礙表示等；「截圖不包含連結去哪」，App Shot 讓模型拿到更豐富的上下文，並在 token 效率上做了工程取捨。
  • Computer Use 最深遠的用例是「代理測自己的代碼」：過去 Codex 寫完代碼要人類當 QA；現在代理可自己建、自己測，形成完整 SDLC 閉環。Ari：「有個好玩的地方是，我在開發 Computer Use，於是我有一個 Computer Use 代理在用我的 Computer Use 代理。」
  • OpenAI 一週做出 Decisions API——而且是「克隆 Jev」：Nikunj 直言 Decisions API 是被 Jev 啟發，由 inference 與 infra 團隊「被勾起好奇心」而自發動工，四週前根本不在 roadmap 上，一週內做出原型並開始爬延遲。
  • Decisions API 的真相：不是新模型：完全建立在現有 Luna 權重之上、零樣本。做法是：約束 + 結構化輸出 + 針對 TTFD（time-to-first-decision） 優化推理棧 + 把多個問題並行批次跑。好處是「視覺能力對 Luna 是免費贈送」。
  • 什麼才是「決策模型」的護城河：swyx 逼問——如果只是結構化輸出 + 關掉推理，那人人都有 Jev。Nikunj 承認真正的差異在校準（calibration）與置信度——也就是 RLHF 把模型「往你想聽的方向坍縮」後，仍要保留「你到底多有把握」的訊號。業界對 Jev 的兩大猜測（擴散式非自迴歸生成、或 mechanisic-interp 直接讀取激活輸出）OpenAI 未證實。
  • GPT 平台的「AI 雲」演化：新 API 原語包括 async tool calling（工具跑時模型不必停下來）、mid-turn steering（推理中途注入訊息，屬模型/對齊能力，需訓練）、WebSockets（雙向通訊底座，最早為 GPT-5.3 Codex Spark 上線）、UltraFast 推理。另有 12 小時快取保證（preview）與 cache pre-warming，以及 server-side compaction 與 /compact 手動壓縮。
  • OpenAI 想吃「更高階原語」：Nikunj 以 Stripe 類比——支付之上長出 Stripe 的高階產品；AI 世界的對應物（記憶、儲存抽象、Agents API 該吃多少）仍是開放問題。swyx 總結為「你在造一朵 AI 雲」（EC2/S3 的 AI 原生版）。
關鍵數據／事實
  • GPT-6.1 Sol：成本約為 Astra 的 1/5；若專門看 Computer Use，約為 Astra 的 1/7。
  • Keynote 中提到 Computer Use 速度提升 7 倍。
  • Ari 個人案例：外送備餐訂單原本要 2 小時，Computer Use 用 15 分鐘完成（快 8 倍，省下 2 小時）。
  • Luna 價格曾被下調約 80%，主要來自推理棧效率提升；隨後團隊把目標轉向「跑得最快」。快取讀取成本又降約 25%。
  • 快取保證期由 30 分鐘延長至（preview 中）12 小時；付較高 cache write 費即可鎖定長窗口。
  • 業界過去兩週出現約 100 個 Jev 克隆（swyx 語）。
  • Agents API 已承載 OpenAI 自家產品：Codex 安全功能、當日上線的會議/協作 space。
  • Dots：每個 Dot 擁有一台雲端 Linux 虛擬電腦，可跑完整桌面應用 + 瀏覽器——與過去「雲端瀏覽器」或「你的電腦」不同。
重點引用

「Computer Use 180 度不同於幾個月前……最大的差異是以前它們能可靠地開始任務、但一遇問題就卡住，現在它們非常擅長 debug、擅長重試、擅長自省哪裡行哪裡不行。」——Ari Weinstein

「我認為真正瘋狂的是，團隊在過去幾個月做到的，是 Computer Use 現在完成任務比普通人還快……下一個前沿是讓它字面意義上的超人。」——Ari Weinstein

「我們沒有為此訓練新模型……這真的就只是 Luna。……基本上就是在 Luna 上零樣本施作，看看效果如何。」——Nikunj Handa 談 Decisions API

「大家很快就發現 Jev 出來後——四週前這完全不在開發雷達上。」——Nikunj Handa（swyx：「我想你是貴實驗室第一個克隆並採用它的。」）

「我們都還在過程中，而且我們之中有些人比世界上多數人更早學會信任這項技術……所以我們有責任透過做可靠的東西、做對的安全檢查、在做出後果性操作（如付款）前取得用戶同意，來逐步建立信任。」——Ari Weinstein

「你其實是在造一朵 AI 雲……你在做 AI 原生的 EC2、S3。」——swyx 總結

技術詳情
  • Async tool calling：工具呼叫耗時長時，模型不必暫停推理，可 kick off 工具後繼續推理，再回頭檢查結果。
  • Mid-turn steering：在模型推理過程中注入訊息；主持人強調這部分屬模型對齊能力（需訓練），非純 harness 技巧。
  • WebSockets：提供與模型的雙向通訊，支撐 async reasoning 與訊息注入。
  • Decisions API：無 reasoning、小模型、並行推理——因此快，但「不太擅長長程、複雜任務」；OpenAI 稱「如何把兩條路線結合仍是開放研究」。
  • 快取工程：提出 cache diagnostics 工具，供開發者找出快取命中掉在哪；建議以「cache-aware」方式設計應用。
  • 壓縮：Agents API 內建 compaction；Responses API 提供 server-side compaction（過閾值自動壓縮）與 /compact（手動、全控制，大型 coding agent 偏好）。Codex 開源 harness 已實作檔案式的新型壓縮實驗。
  • UltraFast 與硬體：swyx 提到 GPT-5.3 Codex Spark 明確歸功 Cerebras；對「UltraFast 是否也與 Cerebras 相關」，OpenAI 不確認也不否認，且 OpenAI 亦有自研硅。
行業 insight
  • 護城河的時間尺度被壓縮到「週」：一個領先推理 API（Jev）出現後，OpenAI 一週內克隆出等價原語。稀有資產不再是「誰想到」，而是推理棧效率、快取基建、分發與可靠性。
  • 「模型 → harness」的耦合紅利：Ari 明言「我們在自己的 Computer Use harness 上訓練模型」，因此用官方 harness 有速度/成本/準確度優勢，自建 harness 很難。這與 Latent Space 前集（Thariq）「官方 harness vs 自建 harness 的杠鈴效應」互相呼應。
  • Agents API 是「平台收編 harness」的動作：當把 Codex harness 做成 API，OpenAI 同時變成「AI 雲」的 PaaS 層。
前後脈絡

本集是對前一天 Dwarkesh「Computer Use 沒進展」論點的正面反駁——Ari 稱「他是很難取悅的人，但我們在努力」。同時與 9/29 的 Thariq 集構成組合拳：Thariq 談 harness 可程式化（Claude Mods），Ari/Nikunj 談 官方 harness 通過 API 收編——兩者從不同方向指出「agent 外殼」已是主戰場。與 9/27 Cognitive Revolution「Hugging Face 事件＝共謀」相比，本集對安全的口徑是工程與信任基建（權限、同意、最小授權），而非治理。

爭議點
  • 「比普通人快」缺乏公開 benchmark：Ari 稱速度提升「無論怎麼量都一致」，但強調不同 harness 配置各異，未給單一公開數字；7 倍為 keynote 口徑。
  • Decisions API 是否只是行銷命名：swyx 直指「結構化輸出 + 關推理，人人可做 Jev」；OpenAI 的差異（校準、置信度）尚未在首版體現，坦承要等後續模型。
  • 安全性由「自己 dogfood 後再教開發者」：付款等後果性操作要求用戶同意，但 swyx 自曝「把十幾萬美元的事 yolo 給 Computer Use」，暴露早期採用者的風險胃納。

Machine Learning Street Talk （主持：Tim Scarfe；嘉賓：Leonardo de Moura）

Who Checks a Proof No Human Can Read? — Leo de Moura（綠勾會說謊：當 AI 攻破 Lean 的內核） 發布：2026-09-30 03:19 UTC（北京 11:19）｜片長 74:19

嘉賓背景

Leonardo de Moura——Lean 定理證明器的創造者、Z3 SMT solver 的共同創造者；Lean FRO 首席架構師與共同創辦人（該非營利組織約 20 人），並任 AWS 資深首席科學家。

核心論點
  • 「綠勾會說謊」（cold open）：Lean 的信任基礎是極小的 trusted kernel——Lean 本體巨大且「有無數 bug」，但你只需信任 kernel。然而 kernel 本身也會有 bug，於是出現了對它的soundness 攻擊。
  • Collatz 事件：兩顆 kernel，兩個 bug：約一週多前，一份 Collatz 猜想的（反）證明被提交，宣稱同時被 Lean 官方 kernel 與主要外部 kernel nanoda（Rust 實作）接受。實際情況：nanoda 的 bug 早一步被修（fix PR 在 Lean issue 前一天合併），而該「證明」利用 nanoda 的舊 bug + Lean 官方 kernel 的另一個 bug，是兩個完全不同的 bug。
  • 「極可能由 AI 生成」：de Moura 指出證明中含有「一堆為了製造 hash collision 的怪異項，完全無關緊要」——這正是為了騙過 nanoda。他並說：「我們沒有耐性做這種低階實作，但 AI 有耐性。」
  • 這會持續發生：AI 極擅長挖掘 kernel 的 soundness bug。社群正在討論：對「造出金剛不壞 kernel」的人發懸賞（撐過 X 個月不被攻破即得錢）、簡化 kernel以便驗證、資助 Mario Carneiro 把 kernel 本身證明為正確。
  • 安全靠透明與多重 kernel：Lean 的 comparator 會匯出證明並在沙箱中檢查（防使用者用 metaprogramming 注入假證明、甚至呼叫 C 函數破壞記憶體）。本次教訓之一是 comparator 應永遠自動下載最新版 nanoda，否則就會被舊 bug 騙過。
  • AI 也能幫 Lean 反超 Rust：Kim Morrison 用 Claude agent 把 zlib 從 C 移植到 Lean，讓它通過 C 版測試套件，並證明「對任何壓縮級別、任何資料，壓縮再解壓都還原原始資料」。de Moura 原本認為「今年初這完全超出 AI 能力、毫無希望」。
  • 更意外的結果：Lean 一向擅長「樹/項」操作、不擅長陣列，de Moura 原以為「永遠無法競爭」；但 Kim 讓 AI「放手瘋狂優化」後，效能超越了官方 Rust 實作。他推論下一步：給 AI x86 語義，就能讓它寫彙編並證明屬性——因為「你必須證明定理，你不能作弊」，這是強訊號引導搜索。
  • 證明只認證「人類選擇的規格」：這是全集的漏洞核心——形式化能保證「實作符合規格」，但規格本身對不對，仍由人負責。
  • AI 缺的是抽象，不是聰明：Tim 的比喻——AI 是「往 embedding 空間照手電筒」，需要人類給出有趣視角、種子解與明確目標才能「奇蹟般」奏效。de Moura：「它非常有限……感覺它們只是醒來、沿著上一個留下的麵包屑走下一步，它們並沒有以有意義的方式改變自己的權重。」
  • 能力≠理解，但驗證護欄仍關鍵：即使模型 99.99999% 正確，我們仍需要 certificate。AlphaProof 走的是 MCTS 混合（真正 neurosymbolic）；而 2025 年 IMO 金獎路線卻改用純神經網絡——他們下棋時能生成約 91% 合法走法，但「沒有硬約束」。
  • 作者身份與人的位置：de Moura 認為人永遠在迴路中，至少在規格層——「說軟件該做什麼，永遠是我們的責任」。他對「開發者是否變冗餘」的態度是：「那會像任務完成……也許我就能只做那些不必工作的軟件。」
關鍵數據／事實
  • Lean FRO：非營利，約 20 人；採用大教堂（cathedral）模式維護核心（由中心實體決定什麼能進核心），與社群圖書館（Mathlib、bazaar 式）分層。
  • nanoda：Rust 實作的外部 Lean kernel；其修復 PR 合併於 Lean issue 立案前一日。
  • Lean 上游 issue 14576「Kernel accepts wrong-structure projections, allowing an axiom-free proof of False」＝官方 kernel bug；PR 14577 為 de Moura 的修復。
  • Boris Alexeev 提交的形式證明達 120 萬行 Lean——「沒人想逐行檢查」。
  • Lean 從 1 到 4 的演進、Mathlib 的成長與「Mathlib as infrastructure」（Formal Frontiers）為中段主線。
  • 贊助：Parallel（agent 用 web search / extraction / deep research API）。

技術詳情
  • Trusted kernel 模型：整個 Lean 不必被信任，只需信任小 kernel；並行存在多個獨立 kernel（含 Rust 的 nanoda、digama0 的 Lean4Lean），以冗餘換取安全。
  • 攻擊面：metaprogramming 與 Lean 擴展性可被用來注入假證明，理論上甚至能呼叫 C 破壞記憶體；comparator 以「匯出證明 → 沙箱檢查」隔離此風險。
  • Dependent types 白話解釋、Lean 4 的可擴展性、DSL 隱藏複雜度、以及社群可不經協調自行實作擴展。
  • AlphaProof：MCTS 式 hybrid neurosymbolic；與後來「純 agentic LLM 拿 IMO 金獎」形成路線對比。
  • CPU 上的正式驗證實例被引用為對照：CompCert（編譯器驗證）、seL4（微核心驗證）。

  • 形式化驗證從「實驗室」走向「被攻擊的公共基礎設施」：當 AI 能大規模產出證明、也能大規模尋找 soundness 漏洞，驗證器本身就變成安全目標——這是「AI 安全」在數學層的具體投影。
  • 「可驗證性」是 AI 時代最硬的護城河：與同日 Latent Space 的 Computer Use / 兩日前硅谷 101 的評測數據形成同一條主線——能自動驗證的訊號，比產出本身更稀缺。
  • 規格／定義／抽象的人類責任上移：模型負責搜索，人負責「選定義、判斷抽象、策展 Mathlib、檢視 certificate、決定哪些問題值得投入」。
