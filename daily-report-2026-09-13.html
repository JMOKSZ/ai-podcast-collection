[AINews] DeepSeek v4.1-Flash：763B-P8B-D16B 全新因果 Encoder–Decoder 架構、帶視覺，「巨鯨歸來」🎙️

發布：2026-09-12 05:56 UTC · 類型：AINews 週報（覆蓋 2026-09-09 至 09-10）

主題：DeepSeek 在 v4.x 世代以「介於大版本之間的中間論文」策略，每次端出一個極度聚焦的架構改進且命中率近 100%（Math/GRPO、Coder、R1、以及近期的 Manifold Constrained Hyperconnections、Compressed Sparse Attention）。在 R1 引爆後 DeepSeek 沉寂約一年、讓 GLM 與 Kimi 領跑開源，如今以 V4.1-Flash 回歸——用一個「看似只有 v4.1 小版本號」的命名，掩蓋了其實是全新架構家族的事實。

核心論點：

  • ① 命名是「閱讀理解測試」：官方刻意只標 v4.1 Flash，實際上做的是全新架構，並軟退役 V4 Pro、全面轉向新家族。作者提醒：只讀版本號與 benchmark 標題的人，正是 DeepSeek 想「愚弄」的對象。
  • ② 真正的突破是 prefill／decode 分離：沿用 MoE 記號擴展為「763B-P8B-D16B」——總參 763B，輸入/prefill 主動 8B、輸出/decode 主動 16B，稀疏度僅 1–2%。配合 Sliding-Window Attention Bounded Replay 等新技巧，KV cache footprint 可低至 V4 Flash 的 1/8，對長時程 Agent 更省更快。
  • ③ 原生視覺、無縫整合：不需另等獨立視覺模型，直接把視覺 token 交給骨幹處理（3×3 pixel unshuffle，而非更常見的 2×2），被評論者指「與近期中國同儕（如 Kimi K3）的視覺前端有顯著差異」。
  • ④ 後訓練哲學與 Jie Tang 一致：DeepSeek 明確表示「改進數據品質的 ROI 已遠超鑽研新奇後訓練演算法」——Jasper Lu 稱此為「值得注意」，因為 DeepSeek 一向是最先開拓新演算法／架構的實驗室之一。

關鍵數據（獨立評測）：

  • Artificial Analysis Intelligence Index：40（高於 V4 Pro 0813，低於 GLM-5.3-Flash）。
  • AutomationBench-AA：69%——追平 GPT-6 Astra（69%）、高於 Grok 4.6（67%）；比 V4 Flash 0731 提升 15 分，比 V4 Pro 0813（57%）高 12 分、比 GLM-5.3（62%）高 7 分。
  • GDPval-AA v2：+164 Elo（1468 → 1632），反超 Kimi K3（1584）。
  • AA-LCR v1.1：84%——與 GPT-5.6 Sol、Gemini 3.8 Flash 同級。
  • 價格：$0.30 / 1M 輸入、$1.20 / 1M 輸出，cached input $0.006 / 1M，另有 50% 離峰折扣；1M-token 上下文、文字＋圖像輸入、MIT 授權。
  • 成本效率：雖是「最囉嗦」的模型之一（平均 89k tokens/題，比 GLM-5.3 71k 多 25%、比 V4 Pro 55k 多 62%、甚至高於 Fable 5.1 78k 與 Claude Opus 5 73k），但 每題僅 $0.27，約為 GLM-5.3（$2.01）與 Kimi K3（$2.00）的 1/7、V4 Pro 0813（$0.67）的 1/2.5。
  • Vals Index：#1 開源權重模型（超越 Kimi K3），每測試 $0.30，是開源前十中最便宜者。

技術詳情（架構與系統）：

  • Sebastian Raschka 稱之為「大翻修（big overhaul）」，直言「他們應該叫它 DeepSeek V5」，並把 Encoder–Decoder 設計列為與前代最關鍵的分野。
  • 技術讀者形容這是「保守／老研究想法 ＋ 前沿效率／硬體工程」的奇異混合；Stochastic Chasm 把設計哲學對比 HySparse、NSA 與 DeepSeek 自家 V4 的 CSA/HCA，總結為「local sliding-window 分支 ＋ sparse retrieval 分支」的混合，並指此稀疏／局部混合正成為行業模式。
  • TeortaxesTex 指出 DeepSeek 一貫在前 N 層做不尋常的事（過去 dense 或 hash-routed，如今 SWA-only），推測反映「早期層反覆訓練困難」；並稱整個 stack「降到 40 層，其中可言僅 20 個真正 decoder 層」。
  • Nrehiew 從報告摘出基建細節：dispatch 策略以降長尾停頓、router replay（沿用前一 checkpoint）、dataset-level capping 管理「短 completion 的 off-policy 效應」、丟棄機制、bounded off-policy ratio 與 loss masking、新 checkpoint 更新時持久化 KVs 與 routers；末端有 對 40+ 教師模型的 full-vocab OPD。其 KV 大小約 ~890 bytes/token。
  • Stochastic Chasm 推斷 KV cache 用了 QAT（量化感知訓練）——可解釋為何在 FP4 KV cache 下表現優於同儕。
  • 本地部署可行性（大主題）：Fraser Price 全精度 V4.1-Flash＋DSpark 在 4×Max-Q、僅 64GB 系統 RAM 上跑到 200 TPS（把 200GB 的 Engram/hash table offload 到 NVMe）；後續在 4×RTX Pro 上提升到 300+ TPS、峰值 RAM <32GB（自訂 vLLM fork＋SSD 支援）；antirez 用 DwarfStar 在 128GB M5 Max 上以 SSD 串流跑得「意外地快」。
  • 推理基建：vLLM 新版把 DeepSeek-V4 的 shared experts 融進 MegaMoE，Mooncake Store 可 offload decode KV。

爭議點：TeortaxesTex 反覆唱反調——指 DeepSeek「出的是內部研究產物而非產品」，常見內部評測高、外部穩健性弱、脆弱、技能缺口怪異；稱部分評測「非常奇怪」（尤其 AutomationBench 第一與 CritPt 退步）；並說多人 Agent「DSH agent teams」在缺乏清晰模組化時反而降質（子代理產出 slop、浪費 token），某些情境下「單打」勝過「團隊」。另一方 Shikib Mehri 則反駁「研究已死」的結論，認為槓桿面只是從架構擴展到數據工廠與獎勵設計。

The Rise of the Forward Deployed Engineer — and How To Do the Job Right 🎙️（客座：Vinoo Ganesh）

發布：2026-09-12 15:01 UTC · 類型：深度長文（Latent Space 客座專欄）

主題：FDE（Forward Deployed Engineer，前線部署工程師）已成為 AI 圈最熱門的職位——實驗室、初創與 PE 都在招「坐進客戶營運裡解決問題」的工程師，但幾乎沒有人對這個角色的目的與玩法有共識。作者以自身三次搭建 FDE 職能的經驗（Palantir／Citadel／Kepler），系統拆解「什麼才算 FDE、如何做對」。

嘉賓背景：Vinoo Ganesh——Kepler（為 AI 打造「決定性基礎設施／ground truth」）CEO；此前在 Palantir 領導 Spark、並一手打造把軟體工程師轉成 FDE 的輪調專案 Project Frontline（約 250 人經此計畫，許多人如今在 OpenAI、Anthropic、xAI、Anduril 帶領 FDE 團隊）；再之前在 Citadel 主管 business engineering。曾在 Bagram 空軍基地前線部署。

核心論點：

  • ① 「FDE」一詞已被濫用到幾乎無意義。同樣兩個詞，實際描述的是「第二次通話才出現的 sales engineer」、「會寫 Python 的背配額業務」、「帶筆電與 SOW 的顧問」等根本不同的工作（不同匯報線、不同激勵）。難怪 YouTube 留言半數都在問「這不就是重新發明顧問業？」
  • ② 低垂果實已摘完，價值遷移到「最後一哩」。能被「一套產品原樣賣給一千家公司」解決的問題大多已解決；剩下的藏在牆內、流程雜亂、幾乎無法從外部推斷。「你能不能從 discovery call 推斷一家公司如何關帳」——答案是不能。所以人人都突然「forward deployed」。
  • ③ FDE 的工作是「收集名詞與動詞（collect nouns and verbs）」。同一個概念常至少有四個名字（sales 說 customer、ops 說 client、finance 記 billing entity、engineering 寫 org_id），名稱是表層，底下是營運模型（文化）。「名詞」是公司當作真實的東西，「動詞」是這些東西如何流動（一筆交易如何入帳、關帳前什麼必須成立、半夜十一點誰批准例外、而那個人休假時怎樣）。這些幾乎從未寫下、是活出來的，價值極高，也因此「你沒法直接要」。能藉名詞動詞進行代理（proxy）一家公司如何運作。
  • ④ 產出必須是「產品」，不是一個開心的客戶。解決眼前問題令人滿足、且當週就有人感謝你——但那是 solutions architect 的職責。FDE 存在的唯一理由，是把現場所學變成每個未來客戶都能拿到的東西。「一個滿意的客戶、上遊什麼都沒變」= 失敗：你拿到了上下文，卻在本地花掉了。
  • ⑤ 護城河在哪：不是模型（每月貶值、且本來就是租別人的）、不是人才（所有人競標同一批人、價格已見底）、也不是任一家客戶的地圖（抽取幾乎免費，一下午就能草擬）。草稿不是資產，「知道哪些部分是錯的」才是資產——而那只來自被修正過。
  • ⑥ 匯報線不是行政細節：把職能指向 sales，激勵就變成「拿下眼前這單」；指向 product，每次部署都被要求產出「下一次部署能起跑的東西」。Kepler 從第一天就把 FDE 設為產品團隊的延伸。

關鍵數據／事實：

  • Phoenix 事故（2013，Palantir）：設計乾淨的交易存儲 deployed 到銀行後，真實財務數據有測試數據沒有的洞——空白 timestamp 落到 epoch，retention 邏輯於是對 1970-01-01 迄今每個窗口都請求十分鐘桶，產生約 230 萬個 keyspace；Cassandra 每 file handle 約需 5MB，伺服器 OOM，重啟需 14TB RAM，程序等同判死。根因不是缺用戶研究，而是「從未站在那棟樓裡、讓系統對著生產數據跑」。
  • Project Frontline：約 250 人經此輪調，校友遍布 OpenAI、Anthropic、xAI、Anduril 的 FDE 團隊。
  • 「vinoo.groovy」：為一個數據保留需求臨時寫的 groovy 腳本，本應活不過一週，一年後卻跑在近 10 萬人規模的客戶上、還掛著他的名字——「每個你交付的捷徑，都變成你日後要養的東西」。
  • Parquet 遷移：近一年推動客戶從 CSV 轉 Parquet，被一位數據品質工程師屢屢擋下、理由每次都變。FDE 進場觀察：她把 CSV 從 S3 拉到 Windows 筆電、雙擊打開、肉眼看行——那就是她的數據品質檢查（Parquet 當時無原生檢視器，等於要拆掉她唯一的工具）。當晚做出 Parquet viewer，兩天後她批准遷移，pipeline 執行從約 17 小時降到 2 小時。
  • 「三家公司要同一功能」相對不值錢；「三家公司需要 provenance 層無法表達的東西」才是真信號，且通常悄悄到來——表現為同一位工程師第三次繞過同一限制。
